Cross-Role Visibility Matrix

Family Cube runs on multiple physical devices at once — 2 parents, 2-3 kids/teens, 1-2 grandparents, each on their own phone. Every prior audit this session (quest_action_bible.html, quest_lifecycle_matrix.html, event_lifecycle_matrix.html) traced one actor's lifecycle through one scenario at a time. This pass asks a different question: when Person A takes an action, what does every other role see on their own screen, at that same moment — live via a realtime subscription, eventually via the next manual refresh, or not at all? This document does not repeat findings already recorded in those three docs (the pool-claim CAS fix, the ride-slot CAS fix, the memberIds visibility fix, etc.) except where restating the mechanism is needed to explain a new simultaneity finding.

How this was built — two phases, in order, per explicit instruction. Phase 1 (§1) is a real-world scenario list — a product researcher's lens on what a real family of 4-6 people running this app simultaneously would actually hit — written before opening any additional code beyond what the three prior docs already established. Phase 2 (§2 onward) traces each scenario against the current code, with an exact file:line citation for every claim. Per this project's standing "don't hallucinate, all real" instruction: anything that would need two physical devices or a running simulator to confirm with certainty is labeled Not runtime-tested rather than asserted. Update: a follow-up implementation pass has since fixed all five V-A findings from Phase 2 (V-A1, V-A3, V-A4, V-A5 with real code changes; V-A2 re-assessed as architecturally correct, no change needed) — see each finding's own "Implemented" note for what changed and store/choreStore.ts/store/familyStore.ts/store/kidRequestStore.ts plus migration 20260820121500_realtime_members_kidrequests_pqa.sql for the actual diffs. The scenario-tracing prose below is left as originally written (including "not implemented — research pass only" phrasing in a few spots) since it remains an accurate record of what was found; only the tag/verdict and a new "Implemented" paragraph were added per finding to keep the document from asserting a now-stale state.

1 · Phase 1 — simultaneous cross-role scenarios (written before re-opening component code)

Plain product thinking: a real family of 4-6 people, each on their own phone, all with the app open at various points in the same afternoon. What does each role's screen show at the moment another role acts?

A. Chore state changes

  1. V1 — A kid claims a pool bounty. Do siblings' Chores tabs update live to show it's taken?
  2. V2 — A parent assigns a chore directly to a kid. Does the kid's Hub show the new chore without reopening the app?
  3. V3 — A kid submits a chore for review. Does the parent's Chore Review deck update live, on both parents' devices if there are two?
  4. V4 — A parent marks a chore private/parent-only after a kid already saw it as a household chore. Does it vanish from the kid's device, or linger?
  5. V5 — A teen declines a chore back to the pool. Does a sibling browsing the pool at that moment see it appear live?

B. Calendar / event changes

  1. V6 — A parent edits an event's time. Does the assigned kid's Calendar reflect the new time immediately, even if the kid is viewing a different day/week than the one edited?
  2. V7 — A parent creates an event assigned to two kids (multi-select). Do both kids see it land on their own Calendar at the same time?
  3. V8 — A kid requests a new event (needs-approval flow). Does the parent see the pending-approval badge live, or only on next open?
  4. V9 — Two parents are both looking at the same day's Agenda view. One deletes an event. Does the other parent's screen drop it immediately?

C. Approval & payout visibility

  1. V10 — A parent approves a kid's chore submission. Does the kid see the "approved" status AND the new coin balance land in real time, or do they have to reopen the app for the coins?
  2. V11 — A parent approves a tutor/cheer service request with a coin bonus. Same question as V10 for that separate payout path.
  3. V12 — A second parent, viewing Household Snapshot, checks a kid's coin total right after the first parent approved a payout. Correct number, or stale?
  4. V13 — A senior/GP submits a receipt for reimbursement. Does the sponsoring parent see a badge/notification appear live?
  5. V14 — A parent denies a cash-out request. Does the kid's own wallet screen reflect the (correct, unblocked) balance live?

D. Claim / race visibility

  1. V15 — Two siblings both tap "claim" on the same pool bounty within the same second. Does the loser's UI correct itself, and how fast?
  2. V16 — A teen claims a ride pickup slot. Does a grandparent who was also eligible see it disappear from their queue immediately, or would they still see it as claimable and tap it?
  3. V17 — Two grandparents both open a sponsored GP-quest claim screen for the same grandchild's chore at once (single-target, not team). Race outcome visibility?

E. Helper / ride coordination

  1. V18 — A parent posts a ride request open to GPs. Does every eligible GP's Hub show it live, simultaneously?
  2. V19 — A GP accepts a ride. Does the requesting parent's EnRoute/dispatch view update live, and does a second GP who was also eligible see the offer close out?
  3. V20 — A driver's live location updates during a trip. Do all interested viewers (both parents, the kid being picked up) see the same position at the same time?

F. Kid-request / parent-reply visibility

  1. V21 — A kid sends a permission/question/medical request. Does it appear on a parent's Hub live, or only after the parent's next app open?
  2. V22 — A parent replies to a kid's request (approve/decline with a note). Does the kid see the reply live?
  3. V23 — Two parents are both looking at the same pending kid-request. One responds. Does the other parent's card update/disappear live, or would they double-respond?

G. System A (parent-to-parent household-task negotiation)

  1. V24 — Parent A delegates a task directly to Parent B. Does Parent B's Household Backlog show the new pending card live?
  2. V25 — Parent B accepts/pushes back/snoozes. Does Parent A see the response live?
  3. V26 — Two parents are both looking at the Household Backlog pool at once; one takes (self-assigns) an item. Does the other parent's pool list drop it live?

The chore itself (chore_tasks.assigned_to_id, if the pool item is a plain household chore being self-claimed) IS realtime-live per §3/§6's findings. But addParentQuest's PULL-mode self-claim ALSO writes a parent_quest_assignments row (status ACCEPTED) — and that half of the state is subject to the same V-A5 gap. In practice: the chore disappearing from the pool view (which is what HouseholdBacklogSection's questPool filter — !parentAssignments.find(a => ...) at line 63 — actually keys off) depends on both pieces of state being current on the second parent's device; since chore_tasks is live but parentAssignments is not, there's a narrow but real window where the second parent's stale local parentAssignments (not yet reflecting the new ACCEPTED row) combined with a live-updated chore row could produce an inconsistent intermediate render. Not runtime-tested to confirm the exact visual effect of that inconsistency window; flagged as a secondary consequence of V-A5 rather than a separate root cause.
