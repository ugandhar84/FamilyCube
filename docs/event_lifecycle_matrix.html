Event Lifecycle Matrix

Full real-world lifecycle audit of Family Cube's Calendar/Events system — store/eventStore.ts, features/calendar/CalendarScreen.tsx, EventFormModal.tsx, EventAssignmentCard.tsx, the features/calendar/components/* view layer, and the shared supabase/functions/call-reminder-sweeper edge function. First calendar/events audit this session — the chore/quest engine audit (quest_lifecycle_matrix.html / quest_action_bible.html) is a separate system and is not re-covered here except where the two share code (the reminder sweeper).

How this was built — two phases, in order. Phase 1 (below, §1) is a real-world scenario list written before any code was opened — plain product thinking about what a family actually runs into with a shared, role-aware calendar. Phase 2 (§2 onward) traces each scenario against the actual current code, one at a time, with an exact file:line citation for every claim. Anything that could not be verified by reading code — would need a running simulator, two physical devices, or a real DST transition to actually observe — is labeled Not runtime-tested rather than asserted as fact, per this project's standing "don't hallucinate, all real" instruction. Four real, reachable bugs were found and fixed this pass (one of them — the memberIds visibility gap — also resolves a second listed scenario, E38, as a side effect); they're marked Fixed inline and summarized in Bugs Fixed This Pass.

1 · Real-world scenario list — written before any code was read

Plain product-lens thinking: what does a real family actually hit using a shared calendar app with roles (parent/kid/teen/senior), recurring events, alerts, and multi-member assignment? This list was written first, as its own step, before opening eventStore.ts or any calendar component.

A. Conflicts / collisions

  1. E1 — Two events for the same person overlap in time (soccer practice + dentist appointment).
  2. E2 — Two different parents each create an event for the same slot for the same kid, unaware of each other.
  3. E3 — All-day event "collides" with a timed event the same day — should that even count as a conflict?
  4. E4 — Back-to-back events with no travel buffer between locations.

B. Recurring events

  1. E5 — Edit a single occurrence of a weekly recurring event; rest of series unaffected.
  2. E6 — Edit "this and all future" occurrences; past occurrences preserved.
  3. E7 — Edit the entire series (retroactive vs. future-only).
  4. E8 — Delete a single occurrence; series continues without it.
  5. E9 — Delete the entire series.
  6. E10 — A one-off single-occurrence edit, then later the whole series is edited — does the earlier edit get silently clobbered?
  7. E11 — Recurring event's end date / occurrence count actually stops generating new instances.
  8. E12 — A month with 5 of the target weekday captures all 5.
  9. E13 — Viewing far-future months — are instances virtualized, not literally stored per-occurrence forever?

C. Multi-member / helper coordination

  1. E14 — Event assigned to multiple family members — each sees it on their own calendar/filter.
  2. E15 — A "ride" event created by one parent, driven by another parent or a grandparent helper.
  3. E16 — An assigned member is removed from the family — what happens to events referencing them?
  4. E17 — A helper (GP/teen) accepts or declines — does the requester get notified?
  5. E18 — One assigned member edits the event — do all other assignees see the update?
  6. E19 — One assignee "removes themself" — does it delete for everyone or just unassign them?
  7. E20 — Two people race to claim/accept the same open helper slot simultaneously.

D. Alerts / reminders

  1. E21 — Lead-time alert fires at the correct local wall-clock instant regardless of server/device timezone.
  2. E22 — All-day event reminder semantics vs. a timed event's "X min before start."
  3. E23 — Reminder for an event whose time was edited after the original reminder already fired — does it re-fire for the new time?
  4. E24 — Reminder for a deleted event must not fire after deletion.
  5. E25 — Multiple reminders per event (e.g., a day before AND 30 min before).
  6. E26 — Push/VoIP token missing or stale for the assigned member — reminder silently fails.

E. Timezone / DST

  1. E27 — Family travels; device timezone changes — do displayed times/reminders still resolve correctly?
  2. E28 — DST spring-forward/fall-back — a weekly recurring event's wall-clock time should stay fixed, not shift an hour.
  3. E29 — Event created in one timezone, viewed by a family member's device in a different timezone.
  4. E30 — Reminder lead-time calculation crossing a DST boundary.

F. Lifecycle edge cases

  1. E31 — Event spans midnight (11pm–1am) — which day(s) does it render on?
  2. E32 — Deleting an event that another system (chore, notification) already references.
  3. E33 — Editing an event after a reminder already fired — no duplicate/stale re-fire.
  4. E34 — All-day vs. timed event — sorting/display/conflict logic differ correctly.
  5. E35 — Past events — can still be edited/deleted, and does that make sense?
  6. E36 — Event created with end time before start time (bad input) — validated?
  7. E37 — Very long-duration event (multi-day, e.g. vacation) renders across days correctly.
  8. E38 — Event search/filter matches title, notes, assigned-member name, and respects role scoping.
  9. E39 — Drag-to-reschedule (if it exists) updates every necessary field atomically, including timezone stamp.
  10. E40 — Color/category assignment is consistent, dark-mode-safe, has a sane default.

G. Cross-role permissions

  1. E41 — Kid/teen visibility: full family calendar, or just their own?
  2. E42 — Can a kid edit/delete an event a parent created?
  3. E43 — Kid/teen-created event that auto-assigns a parent needs an approval/veto flow.
  4. E44 — Senior role's visibility rules vs. parent.
  5. E45 — "AI conflict detection" — does it actually compute time-overlap, or is it cosmetic?

2 · Alert/reminder timing for events — re-derived from scratch

Priority area #1. The task explicitly warned not to assume this is fine just because chore_tasks.due_time got fixed this session — traced independently for events' own code paths (calendar_events.start_time, .date, .timezone, .alert_call_lead_minutes).

Not a gap E21 — Local wall-clock → correct UTC ring instant for events

store/eventStore.ts:279-286 (toRow) · features/calendar/components/eventForm/types.ts:104-106 (fmtTime) · supabase/functions/call-reminder-sweeper/index.ts:83-108 (localWallClockToUTC)

Traced: EventFormModal.tsx:361 writes time: fmtTime(primaryKidRideDate) where the imported fmtTime(d: Date) (from eventForm/types.ts:104, confirmed the actual import at EventFormModal.tsx:43) returns 24-hour "HH:MM" — not the 12-hour "2:05 AM" style the sweeper's own code comment warns about for chore_tasks.due_time. That comment describes a different, older time-picker helper used by the chore form; the event form's own time field is 24-hour throughout. eventStore.ts's toRow() (line 285) stamps timezone: Intl.DateTimeFormat().resolvedOptions().timeZone on every write — confirmed present, not just described. The sweeper's localWallClockToUTC() reads e.date/e.start_time/(e as any).timezone (index.ts:171-181) and does the same DST-aware offset-diffing used for chores.

Disposition: Verified correct for events specifically, not by inheritance from the chore fix. The sweeper's to24Hour() regex (index.ts:51-64) handles both 12h and 24h input defensively, which is harmless here since events only ever produce 24h strings — it's dead-code-safe, not a live bug for events.

Fixed E24 — Sweeper had no deleted_at filter — a deleted event's reminder could still ring

supabase/functions/call-reminder-sweeper/index.ts (calendar_events + chore_tasks queries)

Scenario: A parent creates an appointment with alert_call = true, then deletes it a minute before the lead-time window. deleteEvent() (eventStore.ts:805-826) is a soft delete — it stamps deleted_at/deleted_by via dbUpdate, it does not remove the row. The sweeper's calendar_events query (and the chore_tasks query, same issue) selected on alert_call = true and the date window only — no is('deleted_at', null) anywhere in the original query. A soft-deleted event with alert_call still on would still be picked up by the sweep and would still fire a real CallKit/ConnectionService ringing alert to the assigned member(s) for an event they'd already removed.

Fix: Added .is('deleted_at', null) to both the calendar_events and chore_tasks queries in the sweeper.

Fixed E23 — Editing an event's time after its reminder already fired meant it could never ring again

supabase/migrations/20260819080000_call_reminder_alerts.sql:51-57 (original call_reminder_log schema) · supabase/functions/call-reminder-sweeper/index.ts (dedupe block) · supabase/migrations/20260820164500_call_reminder_log_due_at.sql (new)

Scenario: A dentist appointment is set for 3pm with a call reminder; it rings at 2:50pm as expected. The parent then reschedules it to 5pm the next day for a valid reason (dentist called back). call_reminder_log had unique(item_type, item_id) — one row ever, keyed only by the item's identity, not by which specific due-time it was for. The sweeper's dedupe query (index.ts:186-192, pre-fix) checked only item_type:item_id against that log — once an item had rung once, it could structurally never ring again for the rest of its life, including a legitimately new time after an edit.

Fix: Added a due_at column to call_reminder_log and changed the unique constraint to (item_type, item_id, due_at) (new migration). The sweeper now computes a minute-rounded due_at for each candidate ring and includes it in the dedupe key, so an edited time is a distinct key eligible to ring again, while retries of an unmodified item within the 90-second sweep window still collide on the identical due_at and stay deduped exactly as before.

Not a gap E22 — All-day event reminder semantics

supabase/functions/call-reminder-sweeper/index.ts:171-181

Checked: what happens to alert_call on an all-day event, which has no start_time?

Disposition: if (!e.start_time) continue; (index.ts:172, pre-existing, unchanged) — an all-day event with no start time is simply skipped by the sweeper entirely. This isn't a crash or a silent-wrong-ring; it's the sweeper correctly declining to compute a ring time it has no basis for. Whether all-day events should even offer the alertCall toggle in the UI at all is a product decision (EventFormModal doesn't currently hide it for allDay events — see Gaps summary) rather than a code bug in the sweeper itself.

Gap, flagged not fixed E22b — alertCall toggle is shown even when allDay is on, but silently does nothing

features/calendar/EventFormModal.tsx:742-757 (create), :1415-1434 (edit)

The Alert Call toggle and lead-time chips render unconditionally regardless of the allDay switch's state. A parent can turn on "Call me" for an all-day event, pick "10 min before," save it, and nothing will ever ring — the sweeper silently skips any row with no start_time (E22 above). This is a real UX dead-end (the toggle lies about doing something) but is a product/UI decision, not a data-correctness bug — either the toggle should hide for all-day events, or all-day events need their own "remind me at HH:MM the day of" semantics. Left unfixed as a design call outside a targeted bug-fix pass.

Not runtime-tested E26 — Missing/stale VoIP push token

supabase/functions/call-reminder-sweeper/index.ts:196-224

The sweeper resolves tokens via voip_push_tokens and logs the ring even with zero tokens found (index.ts:222-224, comment confirms this is intentional — "the window has passed either way"). Whether token registration itself is reliable (app foreground/background re-registration, token rotation) is entirely outside this codebase's client-visible surface for this pass — flagged as not runtime-tested rather than asserted working or broken.

4 · Multi-member / helper coordination

Priority area #3.

Fixed E20 — Race: two GPs (or a GP and a teen) both claim the same open helper/driver slot

features/hub/senior/FamilyNeedsHandSection.tsx:67 (pre-fix) · features/hub/TeenView.tsx:93-98 (pre-fix) · store/eventStore.ts (new claimHelperSlot)

Scenario: A parent flags a ride as isOpenToGrandparents + isOpenToTeens. Two grandparents both have the Hub open and both tap "I'll Drive" within the same round-trip window; or a GP and an eligible teen both tap their respective claim button on the same event near-simultaneously. Both these call sites called updateEvent(ev.id, { helper: active.name, helperStatus: 'confirmed' }) directly — eventStore.ts's updateEvent → dbUpdate (line 289-293, pre-fix) issues a plain UPDATE calendar_events SET ... WHERE id = ? with no conditional clause on the current helper_status. Postgres last-writer-wins with zero error surfaced to the loser — both devices' optimistic local state shows themselves as the confirmed driver, but only one of them is actually assigned server-side; the "loser" would believe they're on the hook for a ride they aren't.

Root cause: Same shape as the already-fixed chore bounty-claim race in choreStore.ts's claimBounty (search .is('assigned_to_id', null) there) — no compare-and-swap anywhere in the events mutation surface.

Fix: Added claimHelperSlot(id, role, claimantName, extra?) to eventStore.ts, mirroring claimBounty's pattern exactly: optimistic local update applied immediately, then the real DB write is a conditional UPDATE ... WHERE id = ? AND helper_status IS NULL (or driver_status for the driver role) via Supabase's .is(col, null). If the write returns zero rows (someone else won), the store re-fetches the row from the DB and reconciles local state to the actual winner instead of a bare rollback to "unassigned," so the loser's UI shows who really has it. Routed FamilyNeedsHandSection.tsx's "I'll Drive" (open kid-request pool) and TeenView.tsx's claimPickup (open teen dispatch pool) through it — both are genuine multi-claimant open pools. Left the "Step In" takeover button in the same file (FamilyNeedsHandSection.tsx:204-220) on plain updateEvent, since that's an explicit single-actor displacement of an already-assigned-but-unresponsive helper, not a race over an unclaimed slot — the new conditional guard wouldn't even match there (status isn't null). Also left RideRequestCard.tsx:216 (a parent claiming their own newly-created event) unchanged — single-actor context, not a race.

Residual, smaller-severity note: TeenView.tsx's claimPickup still awards coins client-side immediately after calling claimHelperSlot, before the DB round-trip confirms the claim actually won. If a teen loses the race, they still keep the coins already granted locally — a real but low-severity gap (a coin-ledger reconciliation issue, not a double-booking one) left unfixed since a proper fix needs the coin award to move server-side/transactional, out of scope for this pass.

Fixed E14 — Multi-member (memberIds) assignees were invisible to Calendar's own visibility/filter logic

features/calendar/CalendarScreen.tsx (dayEvents, scopedRangeEvents, matchesMemberFilter — all pre-fix checked only e.memberId)

Scenario: A parent creates one event for both kids via the multi-select "For" picker in EventFormModal.tsx — confirmed this writes memberIds: memberIds.length > 1 ? memberIds : undefined (EventFormModal.tsx:376) and memberId: memberIds[0], so the event has a real primary memberId (the first pick) plus a full memberIds array. EventCard.tsx renders this correctly — it reads ev.memberIds for the "For" avatar row (EventCard.tsx:381-382). But CalendarScreen.tsx's own scoping logic — the senior/GP visibility gate in dayEvents (was line 606-610), the "My Schedule" tab gate in the same block (was line 612), scopedRangeEvents's identical senior gate (was line 625-629), and matchesMemberFilter (was line 559-568, the member-filter-pill logic) — all checked only e.memberId, never e.memberIds. A senior/GP who was the 2nd or 3rd assignee (not the primary memberId) on a shared event would fail the senior visibility check entirely and never see the event at all; any family member's filter pill would fail to surface an event they were a non-primary assignee on; a teen/kid/senior's own "My Schedule" tab would exclude events where they were only in memberIds, not memberId.

Fix: Added e.memberIds?.includes(activeMemberId ?? '') / e.memberIds?.includes(filterMember) checks alongside every existing e.memberId === ... check in dayEvents, scopedRangeEvents, and matchesMemberFilter. Also corrected the "family-wide event" fallback (!e.memberId) to (!e.memberId && !e.memberIds?.length) in the senior gates — previously a multi-member event with memberId unset but memberIds populated (not actually reachable given how the form writes it, but not guaranteed by the type) would have been misread as "family-wide, show to everyone."

Not a gap E15/E17 — Ride created by one parent, driven by another; accept/decline notifies

features/calendar/EventAssignmentCard.tsx (whole file) · features/hub/parent/RideRequestCard.tsx

Traced: EventAssignmentCard's Accept/Reassign/Decline flow (lines 62-84) correctly gates on needsMyDecision = isMe && status === 'pending' and writes back through updateEvent with clear status transitions (confirmed/pending-for-reassign-target). confirmDecline hands off to the other parent automatically (line 67-73) with a note recording who declined and why. eventStore.ts's updateEvent has a dedicated auto-open-to-pool behavior on decline (lines 785-788: justDeclined/autoOpenOnDecline) that flips isOpenToGrandparents/isOpenToTeens automatically for Ride-category events, so a decline doesn't strand the request on the creating parent noticing and manually re-opening it.

Disposition: Verified correct. One caveat noted separately below (E15b) about name-based rather than id-based matching.

Gap, flagged not fixed E15b — Helper/driver assignment is matched by free-text name, not member id

features/calendar/EventAssignmentCard.tsx:38 (assignee = members.find(m => m.name === name)) · features/calendar/CalendarScreen.tsx matchesMemberFilter (helper/driverName .includes() checks) · features/calendar/components/EventCard.tsx:340

FamilyEvent.helper and .driverName are stored as free-text display names (not member ids) throughout the event system — a deliberate, pre-existing design choice supporting external, non-family helpers (e.g. a tutor or coach who isn't a family member at all). Every place that needs to know "is this me" or "does this match the filtered member" does a name/substring match (EventAssignmentCard.tsx:38, CalendarScreen.tsx's matchesMemberFilter, EventCard.tsx:340). If two family members share a first name, or a kid free-types a name that happens to substring-match a different member's name, the match could resolve to the wrong person or nobody. This is inherent to the current schema, not a one-line bug — fixing it means migrating helper/driverName to id-based fields with a separate free-text fallback for non-family helpers, a schema-level change out of scope for a bug-fix pass. Flagged as a design-tradeoff gap, not fixed.

Not a gap (graceful, not crash-safe-verified) E16 — Assigned member removed from the family

store/familyStore.ts:223-225 (removeMember) · features/calendar/components/EventCard.tsx:123,334 (assignee = members.find) · features/calendar/CalendarScreen.tsx matchesMemberFilter

Traced: removeMember (familyStore.ts:223-225) simply filters the member out of the local members array — confirmed no code anywhere in eventStore.ts, CalendarScreen.tsx, or EventCard.tsx cleans up calendar_events.member_id/member_ids/helper_name/driver_name rows that referenced the removed member's id or name. Every read site that resolves an assignee does members.find(m => m.id === ev.memberId) (e.g. EventCard.tsx:123) — with the member gone, this returns undefined, and every call site checked (EventCard.tsx's "For" row, "picker" fallback, em-dash placeholder) handles an undefined assignee gracefully rather than crashing.

Disposition: The orphaned id/name reference lingers silently forever (a data-hygiene gap — deleted family members' names could keep appearing as "helper: Grandma Rose" text on old events even after Grandma Rose is removed from the family), but nothing crashes and nothing shows wrong data for a live member. Not fixed — cleaning up historical references on member removal is a product decision (should past events even change once someone leaves the family?) rather than a bug, and no reachable crash was found to justify an urgent fix.

Not a gap E18/E19 — One assignee edits/removes themself from a multi-member event

store/eventStore.ts:779-803 (updateEvent) · store/eventStore.ts realtime channel (lines 295-439)

Traced: Any updateEvent call writes the full row via dbUpdate and every subscribed client picks up the change through the single Postgres Changes realtime channel (ensureRealtime, lines 299-439) — both the day-events and range-events branches update from the same UPDATE payload. There is no separate "my copy" of an event; calendar_events is one row per event regardless of how many members are assigned, so an edit by any one assignee is visible to all other assignees' devices via the same realtime UPDATE, not a per-viewer independent copy.

Disposition: Verified structurally correct — same reasoning the quest audit used for choreStore's single shared Zustand slice, applies here too since there's one row, one channel, and both Day and Range views subscribe to the same channel.

5 · Conflicts / collisions

Priority area #4 (open scope), starting with E45 since it reframes E1-E4.

Confirmed gap, not fixed E45 — "AI conflict detection" does not compute real time-overlap; it's driven entirely by a manually-set boolean

features/calendar/components/AiConflictBanner.tsx:1-8 (own header comment) · features/calendar/CalendarScreen.tsx:224-267 (simulateConflictDetection) · store/eventStore.ts:215,262 (conflict field)

Traced: AiConflictBanner.tsx's own header comment states plainly: "Presentation only: the actual conflict-detection algorithm (simulateConflictDetection) and all state ... still live in CalendarScreen." Read simulateConflictDetection in full (CalendarScreen.tsx:224-267): it takes an already-filtered events array and does const conflicted = events.filter(e => e.conflict) — it reads a pre-existing e.conflict boolean field, it does not compute any actual start/end time overlap between two different events anywhere in the function. Searched every write site of conflict: across the entire calendar feature (eventStore.ts:215,262 — fromRow/toRow passthrough only; EventFormModal.tsx:395 — always initialized to false on create; CalendarScreen.tsx:540 — only ever set back to false when a driver-swap is applied). There is no code path anywhere in this codebase that ever sets conflict: true. The field exists as a column and a type, but nothing populates it from real schedule analysis.

Disposition: This is a real, confirmed gap — the banner's copy ("Scanning for time overlaps, missing drivers, and travel conflicts...") and its pill's label ("Conflict detected") both imply the app is actually detecting scheduling collisions, but the only way hasConflicts (CalendarScreen.tsx:693, dayEvents.some(e => e.conflict || e.helperStatus === 'rejected')) can ever be true is a declined helper — never an actual double-booking. Not fixed this pass: implementing genuine overlap detection (comparing every pair of same-member events' start/end windows, handling all-day vs. timed, handling the midnight-span gap noted in E31) is a real feature build, not a bug fix — flagged as a Known Gap rather than attempted as a quick patch that would risk being wrong or incomplete for a "the heart of the project" area.

Since E45 establishes there is no real overlap-detection engine, whether the UI itself ever visibly warns a parent that they just booked the same kid into two 4pm events cannot be verified as "handled" — it structurally cannot happen today (no code path sets conflict: true from real time comparison). This is the direct consequence of E45, not a separate finding; not re-fixed separately since fixing E45 is the actual fix for this too.

Not a gap E3 — All-day event vs. timed event on the same day is not flagged as a conflict

features/calendar/CalendarScreen.tsx:224-267

Given there's no real overlap engine at all (E45), this specific sub-case is moot the same way — but worth noting as a product judgment call for whenever E45 is actually built: an all-day event (e.g. "Grandma visiting") and a timed event (e.g. "3pm soccer") on the same day are not inherently in conflict in the way two timed events with overlapping windows are. Recorded as a design note for a future real implementation, not a current bug.

6 · Timezone / DST

Not a gap E27/E28/E30 — Sweeper's DST-aware offset computation

supabase/functions/call-reminder-sweeper/index.ts:83-108 (localWallClockToUTC)

Traced: localWallClockToUTC formats the same instant in both UTC and the target IANA zone via Intl.DateTimeFormat, diffs the two to get the zone's offset at that specific instant (not a cached/current-moment offset) — this is exactly the standard technique needed to get DST correct for a date other than "right now," since the function is explicitly computing the offset for the reminder's actual date, not today's date. A weekly event stored as a fixed wall-clock start_time (e.g. "15:00") combined with the family's IANA timezone string will resolve to the correct local 3pm on both sides of a DST transition, because the offset is recomputed per-row from that row's own date, not reused from a stale calculation.

Disposition: Verified correct by reading the algorithm — not runtime-tested against an actual DST transition (no way to fast-forward device/server clocks across a real boundary in this session), but the technique itself is sound and matches the already-verified chore-side fix from earlier this session.

Not runtime-tested E29 — Event created in one timezone, viewed from a different one

store/eventStore.ts:279-286 (toRow, timezone stamped once at write time)

timezone is stamped once, at write time, from the creating device's Intl.DateTimeFormat().resolvedOptions().timeZone — this is correct for computing the reminder's true ring instant (the event's own timezone, not the viewer's). Whether the displayed time on a viewing device in a different zone correctly converts for display (as opposed to just for reminder-firing) was not traced — the client-side render paths (EventCard.tsx, DaySlotView.tsx etc.) all just show the raw stored HH:MM string via fmtTime-style helpers with no zone conversion visible in the code read this pass. This may be intentional (the app might intend "shows the event's own local time, not converted to the viewer's phone zone" — arguably the more useful behavior for a family calendar) or may be an unaddressed gap; flagged as unconfirmed product intent rather than asserted as a bug.

7 · Lifecycle edge cases

Confirmed gap, not fixed E31/E37 — Midnight-spanning and multi-day events are not modeled; DaySlotView has a hard 5am–11pm window with no overflow indicator

store/eventStore.ts:26 (FamilyEvent.date — single date field) · features/calendar/components/DaySlotView.tsx:24-25,34,38-44

Traced: FamilyEvent has exactly one date field (line 26) and a time/endTime pair with no separate end-date — there is no way to represent an event that starts on one calendar date and ends on another at all. Events are fetched strictly by .eq('date', date) (fetchDayPage, eventStore.ts:451) — a hypothetical 11pm–1am event stored with date = the start day would only ever appear in that one day's query, never the next day's, even though it's still "happening" past midnight. Separately, DaySlotView.tsx (the Day view's hour-slot list) hard-codes DAY_SLOT_START_HOUR = 5 / DAY_SLOT_END_HOUR = 23 (lines 24-25) and buckets events by Math.floor(timeToMinutes(ev.time)/60) === hour (line 42-44) only within that 5am-11pm range — an event with a time outside that window (e.g. a 5:30am event, or anything after 11pm) has no matching hour row and is rendered nowhere in this view, with no overflow/"+N more" indicator.

Disposition: Confirmed real, reachable gaps.
