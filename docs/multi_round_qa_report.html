Live incident

Chat Outage — Caused & Resolved

The chat RLS tightening from Round 1 was correct in intent but shipped with two real SQL bugs, neither of which could be caught from an automated CLI session — both only surfaced once a real authenticated user sent a real message.

What happened, in order

1

Real app logs show op ANY/ALL (array) requires array on right side on every message send.

Root cause: the new RLS check compared a value against a jsonb column using array syntax — member_ids was jsonb, not a native array.
2

Fixed by switching to proper jsonb containment. Pushed within minutes.

3

A second error immediately follows: new row violates row-level security policy — a real, legitimate participant is now being rejected.

Root cause: the fallback DM-id parser split the channel id on underscore, but real member ids can themselves contain underscores — fracturing a genuine participant's id so it never matched.
4

Fixed by dropping ID-parsing entirely — participation is now checked solely against the stored, correctly-populated participant list, never by re-deriving it from the channel id string. Verified directly against the real row that had failed before reporting resolved.

Feature build

Multi-Slot Bounty Claiming

A user question ("shouldn't a bounty support at least 2 kids?") surfaced a real gap: the "up to N kids" setting already had a complete UI — a picker, "Full — 2/3 claimed" copy — but the value was saved nowhere, and the claim logic only ever supported exactly one claimant.

What was built

A new table tracks each kid's claim independently. Claiming a slot is atomic — a single database function locks the bounty row, checks the live slot count, and inserts the claim in one transaction, so two kids claiming the last open slot at the same instant can't both win it. Each claim then works, submits, and gets approved or declined on its own — one kid's outcome never affects another's.

Claim (atomic, row-locked)→ Submit (per claimant)→ Approve / Decline (per claimant)→ Payout (independent, no split)

Round 7

Ride/Schedule System — a Real User Report

Triggered live: a kid's ride request never reached Action Needed, and a recurring ride showed a dozen near-identical "no driver" cards instead of one. Root cause was structural — a recurring event materializes as fully independent rows sharing only a series id, with zero propagation between them, so every occurrence needed its own separate driver decision forever.

SeverityFindingLocationStatus
High Assigning a driver to one occurrence of a recurring ride never carried forward — every future occurrence stayed stuck "unassigned" indefinitely, and Action Needed rendered one full card per occurrence rather than one per series. RideRequestCard, ActionNeededSection ✓ Fixed — series-aware propagation + per-series dedup
Medium A kid who named a helper right at request creation matched two mutually-contradictory visibility filters at once — "nobody's looked at this yet" and "a driver was named" — rendering two conflicting banners simultaneously. KidView.tsx — myPendingRides ✓ Fixed — excludes events with a named helper
Medium Deleting just the anchor occurrence of an open-ended recurring series silently ended the whole series at its rolling generation horizon — no error, no signal, the series just quietly stopped producing new dates months later. deleteEventScoped ✓ Fixed — next-soonest occurrence is promoted to anchor before delete

The scoping decision that mattered most

Carrying a driver forward to future occurrences is only safe if it's selective. The initial "yes, I'm driving this" acceptance propagates to every future occurrence — but a later one-off decline, reassignment, or take-over ("I can't do just this Tuesday") stays scoped to that single occurrence only. Without this distinction, a parent's single scheduling conflict would silently reassign the entire rest of a recurring series away from its regular driver — the opposite failure from the original bug, and arguably worse. This same 'this'-vs-'following' split was then carried consistently into every driver-assignment surface across parent, teen, and GP views.

Sign-off

Overall Verdict

All 37 confirmed bugs across 10 rounds are fixed, and every fix from Rounds 7–9 was independently re-verified in Round 10 against real data (the two Critical items against the actual deployed engine, not just source). This span covers the critical self-approval exploit, the critical reward-threshold bypass, two live production incidents this QA effort itself introduced and then resolved within the same session, the delegation-visibility bug a real user actually hit in production, and — the largest single cluster — a full role-by-role audit of the ride/schedule system that found the zero-touch dispatch engine silently corrupting live data on every automated grandparent assignment. The core concurrency-safety pattern (row-locked atomic claims) is now applied consistently across pool quests, GP offers, helper/driver slots, and the multi-slot bounty feature. The recurring-series propagation logic built in Round 7 — carry the driver forward on first accept, but never on a later one-off decline or reassignment — was then correctly reused, not reinvented, across every driver-assignment surface touched in Rounds 8 and 9.

Two things worth naming directly. First, live user reports remain a genuine, distinct source of findings alongside structured testing, not a substitute for it — Round 5's delegation bug and Round 7's ride-visibility bug were both real production reports, not proactive discoveries, and both led to deeper structural fixes than the original report alone described. Second, "the code was fixed" and "the fix was verified against live, real behavior" are different claims, and Round 10 exists because the difference matters: it caught a genuine gap (soft-deleted events still counting against a live constraint) that a second read of the diff alone would not have surfaced. Round 11, still open, extends verification one layer further — confirming not just that the underlying data ends up correct, but that the actual UI action available to each role at each lifecycle step is the right one, role by role, state by state. The remaining caveat from earlier rounds still stands: the bounty claim function's true concurrent-load behavior is sound by code inspection but not empirically stress-tested under real simultaneous traffic.

Test environment: isolated synthetic family (one member per role, including maternal/paternal grandparents), all real Supabase writes, cleaned up after every round. No production family data was read, written, or exposed at any point except the incident window described above, which touched only RLS policy logic, never message content.
