Feature build

Multi-Slot Bounty Claiming

A user question ("shouldn't a bounty support at least 2 kids?") surfaced a real gap: the "up to N kids" setting already had a complete UI — a picker, "Full — 2/3 claimed" copy — but the value was saved nowhere, and the claim logic only ever supported exactly one claimant.

What was built

A new table tracks each kid's claim independently. Claiming a slot is atomic — a single database function locks the bounty row, checks the live slot count, and inserts the claim in one transaction, so two kids claiming the last open slot at the same instant can't both win it. Each claim then works, submits, and gets approved or declined on its own — one kid's outcome never affects another's.

Claim (atomic, row-locked)→ Submit (per claimant)→ Approve / Decline (per claimant)→ Payout (independent, no split)

The scoping decision that mattered most

Carrying a driver forward to future occurrences is only safe if it's selective. The initial "yes, I'm driving this" acceptance propagates to every future occurrence — but a later one-off decline, reassignment, or take-over ("I can't do just this Tuesday") stays scoped to that single occurrence only. Without this distinction, a parent's single scheduling conflict would silently reassign the entire rest of a recurring series away from its regular driver — the opposite failure from the original bug, and arguably worse. This same 'this'-vs-'following' split was then carried consistently into every driver-assignment surface across parent, teen, and GP views.

Overall Verdict

All 82 confirmed bugs across 18 rounds are fixed. Round 18 surfaces two bugs in chores/schedule pre-launch verification: a grandparent's sponsored quest vanishing from her Hub the instant a parent approved it (while her Quests tab correctly tracked it), and a kid's Hub chore card having zero overdue-badge awareness while the Quests-tab card for the same chore flagged it red — both fixed same-session. Earlier rounds' fixes (Rounds 7–9) were independently re-verified in Round 10 against real data. Round 17 surfaces two more bugs: recurring chores' dueDate staying frozen on reset (breaking the missed-cycle streak detection), and recurring event self-claims never propagating to future occurrences (reintroducing Round 7's duplicate-cards bug for the GP/teen self-claim path specifically) — both fixed same-session. This span covers the critical self-approval exploit, the critical reward-threshold bypass, the grandparent chat side-isolation leak, the never-deployed rewards table, four live production incidents (three this QA effort itself introduced and resolved same-session, one discovered and fixed mid-Round-15), the delegation-visibility bug a real user hit in production, and a full role-by-role audit of both the ride/schedule dispatch engine and the kid ride-request UI that found the same shape of bug — correct logic silently unreachable or unreadable by the role it was built for — recurring at every layer of the stack, from a live edge function down to a single missing database table.

Three things worth naming directly, in the order they were learned. First, live user reports remain a genuine, distinct source of findings alongside structured testing, not a substitute for it — Round 5's delegation bug, Round 7's ride-visibility bug, and the Round-13/14 kid-navigation and edit-form incidents were all real production reports or direct user questions, not proactive discoveries, and each led to a deeper structural fix than the original report alone described. Second, correct backend logic and a correct data model are necessary but not sufficient — the driverName/driverStatus field pair was introduced correctly in Round 11, but most of the app's UI simply never learned to read it, producing a coherent-looking but silently broken experience across five separate surfaces at once; the per-role navigation audit (Round 13) found the identical shape of bug one level up, a control that works perfectly for the role it was built for and simply doesn't exist for another. Third, and sharpest: static code reading, however thorough, cannot see a table that was never deployed. The rewards table gap survived every prior round of QA — including agents that read rewardStore.ts directly — because every read path failed silently and every write path swallowed its own error, so the code always looked correct in isolation. Only a real query against the real database surfaced it. The practical implication carried forward: role-coverage audits need to pair reachability checks with a correctness check at the destination, and any fix touching a table, an RLS policy, or an ordering shared between client and server needs a live-database verification pass as a required final step, not an optional deepening one. The remaining caveat from earlier rounds still stands: the bounty claim function's true concurrent-load behavior is sound by code inspection but not empirically stress-tested under real simultaneous traffic.

Round 15 proved one more structural truth: bugs that exist only in the interaction between two roles' code paths are literally invisible to single-role testing, no matter how thorough each single-role pass becomes. A pool chore visible on one role's Hub but invisible on the same role's Quests tab would be caught by per-tab auditing. A chore visible to Kid-1 but invisible to Kid-2 in the pool would be caught by role-coverage testing. But a chore visible to the grandparent in the Hub invitation card but invisible in the Quests tab's filter? That gap exists only at the intersection of two parallel surfaces that never talk to each other, and can only be seen by walking a unified test case through both simultaneously. This round's methodology — one agent, one test family, every step checked against every role and every surface — closes a blind spot the first 14 rounds had structurally. It's also the first QA session where the testing methodology itself was redesigned in response to repeated user feedback that single-pass, parallel rounds kept finding bugs "one at a time" instead of clusters. The follow-on work, if any, should integrate this step-by-step cross-role methodology as a permanent part of the QA process, not something buried in a historical document.
