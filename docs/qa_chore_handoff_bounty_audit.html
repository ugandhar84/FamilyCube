Findings summary

8 scenarios run. 2 genuine NEW bugs found and confirmed live, plus one prior finding re-verified as fixed, and one RLS-policy gap confirmed by direct code read (not exercisable live because the harness has no raw-table-write action for a scoped member session — see §5's own limitation note).

High assign_event_role never clears the opposite driver/helper field-pair — the exact reassign_event bug class, unpatched on its sibling RPC

Root cause. Migration 20260940020000_reassign_event_clears_other_assignee_pair.sql fixed reassign_event to unconditionally null the other role's *_name/*_id/ *_status triple on every write, specifically because a single calendar_events row is only ever supposed to carry ONE live assignee pair (driver XOR helper) — a both-ways ride is always two separate forked rows (features/hub/parent/rideLegs.ts's own forkRideLegs), never one row with both pairs populated. assign_event_role — the RPC used for a FRESH assignment rather than a take-over, added in the same migration wave (20260905110000_event_participant_rpcs.sql) and still live today as of 20260930280000_verify_active_member_across_all_state_rpcs.sql — never received the same fix. Its driver branch only sets driver_name/driver_status/ride_required; its helper branch only sets helper_name/helper_status. Neither branch touches the other pair at all. Confirmed live in §6.9/§6.10 below in both directions: seeding a conflicted row (both pairs populated, reproducing the exact pre-fix shape pass 1 used for reassign_event) and then calling assign_event_role on only ONE role leaves the other role's stale *_name/*_id completely untouched — not just a dangling id (pass 1's Finding #1 shape) but a stale, wrong DISPLAY NAME still sitting in the row. Since eventAssignee() (store/eventStore.ts:290) reads e.helper/helper_name BEFORE driver_name, a fresh, correctly-written driver assignment can be rendered nowhere — every consumer of eventAssignee() would show the stale helper's name/id as "the assignee" instead, with the real new assignment silently invisible.

supabase/migrations/20260930280000_verify_active_member_across_all_state_rpcs.sql:1163-1239 (assign_event_role, live version — driver/helper UPDATE branches, lines 1222-1230, never reference the opposite pair) — supabase/migrations/20260940020000_reassign_event_clears_other_assignee_pair.sql (the fix this RPC needs but never got) — store/eventStore.ts:290-293 (eventAssignee, the read path this corrupts) — features/hub/parent/rideLegs.ts:74-163 (forkRideLegs — confirms a single row is never meant to carry both pairs at once)

High declineChoreHandoff reopens straight to the general pool instead of reverting to the original owner — the offering kid loses the chore entirely, not "back to limbo" but worse: back to anyone

Root cause. The live decline_chore_handoff RPC (20260930280000_verify_active_member_across_all_state_rpcs.sql:79-119) sets assigned_to_id = null, is_pool = true, status = 'todo' on a decline — its own migration comment ("Receiver: 'can't either — put it back' — reopens straight to the pool, no reason required") makes clear this is the intended design, not an oversight. But this means the chore does NOT revert to the original offering member (K3 in this run) at all — it becomes a fully open pool chore any uninvolved kid or teen can claim. Confirmed live in §1.4/§1.5 below: K3 offers a chore to T6, T6 declines, and the chore's assigned_to_id goes to null with is_pool=true — a completely different, uninvolved kid (K5) was then able to successfully claim_pool_quest it away from K3 before K3 ever got a chance to reclaim their own chore. Whether "reopen to the pool" or "revert to the original owner" is the intended product behavior is a real product decision either way — but the task specification's own framing ("verify it correctly reverts to Kid1, not left in limbo") describes a design this RPC does not implement, and the practical effect live-verified here is that a kid who offers a chore to a specific person and gets declined can end up with LESS certainty about the chore than before they offered it — anyone in the family can now take it, not just the person they tried to hand off to.

supabase/migrations/20260930280000_verify_active_member_across_all_state_rpcs.sql:79-119 (decline_chore_handoff) — store/choreStore.ts:2955-2957 (declineChoreHandoff's own comment documenting this as intentional) — features/tasks/lib/deriveCardActions.ts:128 (canClaim — confirms any kid/teen, not just the original owner, sees this as claimable the instant it reopens)
