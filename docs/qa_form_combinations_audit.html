Create / Edit / Delete Form Combinations QA Audit

A fourth QA pass on FamilyCubeApp, scoped to UI/form-state logic in the Event and Quest create/edit/delete forms — features/calendar/EventFormModal.tsx (AddEventModal + EditEventModal), features/calendar/components/eventForm/CategoryFields.tsx, features/quests/components/AddQuestModal.tsx + its section files, and features/quests/components/EditQuestModal.tsx. Three prior passes covered reassign/take-over RPCs, chore handoff/bounty/GP-errand RPCs, and Smart Tasker detection quality — this pass deliberately stays in form/component code, hunting for the same bug shape that produced the tutor-picker lock, the teen/GP eligibility gap, and the dropped return-time bug: a condition gated on a frozen prop instead of live state, a candidate-list filter missing an eligibility check present elsewhere in the same file, or a toggle that doesn't clean up dependent state when turned off.

Method. Static code read only — every finding below was produced by tracing an exact tap sequence by hand through the real component code (not executed), then confirmed with targeted grep cross-references between AddEventModal/EditEventModal, CategoryFields.tsx, AddQuestModal/AddQuestAssignSection/ AddQuestRecurrenceSection, and EditQuestModal. The qa-scratch-family harness was read for context but not invoked — every finding here is reproducible by inspection of state initializers, filter predicates, and toggle handlers, with no ambiguity that would need a live row to resolve.

Findings summary

9 findings from a full read of both event-form files and both quest-form files (2,687 + 520 + 1,304 + 753 lines). Two are the exact "frozen prop" bug shape called out in this pass's brief — one is a literal regression of a bug the team just fixed elsewhere in the same file. High "Needs pickup too?" on a Study event still gates on the FROZEN helperIsRoleFilled snapshot — the exact bug just fixed one section above it

Root cause. EditEventModal declares helperIsRoleFilled at EventFormModal.tsx:1761 as ROLE_HELPER_CATEGORIES.includes(event.category) && !!event.helper — computed once from the event PROP at modal-open time and never recalculated from live state. Commit f1bb4139 (this session) correctly stopped using it to gate the "Change tutor" picker AND the save-time driver patch, specifically because it goes stale the instant a parent picks a new (or external) tutor mid-session. But the fix left one consumer untouched: the "Needs pickup too?" toggle's visibility gate at EventFormModal.tsx:2424 — (helperIsRoleFilled && event.category === 'Study' && editRideRequired) — still reads the frozen prop. Tap sequence: open a Study event that was created with NO tutor at all (event.helper empty, so helperIsRoleFilled = false for the whole session). In the now-fixed "Change tutor / helper" section, type an external tutor name — this correctly reveals "Ride Needed?" (gated on live helperId/editRideRequired, not the frozen flag, per the same commit). Toggle "Ride Needed?" on and pick a driver. The parent now has a fully valid transport assignment (tutor + driver) and should see "Needs pickup too?" to add a return leg — but that section's visibility check still ANDs on helperIsRoleFilled, which is permanently false for this event because it was computed from the event prop before any of these edits happened. The toggle never renders, silently, with no error and no visual indication anything is missing — a parent who read the exact scenario the sibling bug's own commit message described ("an event created with NO tutor that then gets an external tutor + a driver assigned in the same edit session") gets the tutor+driver fix but not the pickup-leg fix, because the same frozen variable leaked into a second consumer the fix didn't touch.

features/calendar/EventFormModal.tsx:1761 (helperIsRoleFilled declaration, frozen from event.category/event.helper props) — features/calendar/EventFormModal.tsx:2424 (stale consumer: (helperIsRoleFilled && event.category === 'Study' && editRideRequired)) vs. features/calendar/EventFormModal.tsx:2327 (the sibling gate on the SAME toggle family, already fixed to use (!helperId || editRideRequired) — live state, not the frozen flag) — the fix should replace line 2424's helperIsRoleFilled with the same live check the tutor-picker fix already established (e.g. !!helperName.trim(), mirroring the Medical/Sports branches right above it on lines 2422-2423 which correctly key off live event.helper for THEIR gate, not a frozen copy).

High "Teens Only" chore restriction has no edit-time UI, no patch field, and no assignment-picker eligibility filter at create time

Root cause, part 1 (edit gap). AddQuestModal.tsx wires up a real teensOnly/setTeensOnly state (line 200) that flows into isOpenToTeens: teensOnly || undefined on creation (line 613) — this is itself the fix for an earlier bug where the field existed in the DB but nothing in chores ever wrote it. But EditQuestModal.tsx has ZERO trace of this field anywhere: no useState seeded from quest.isOpenToTeens, no toggle UI, and neither save() patch branch (locked or unlocked, lines 155-184 and 187-214) ever includes isOpenToTeens in its outgoing patch — despite store/choreAdapter.ts:419/600 and store/choreStore.ts:2019 all fully supporting an isOpenToTeens update through the exact same generic patch path every other toggle in this form already uses. A parent who creates a "Teens Only" chore and later needs to open it up to all kids (or vice versa) has no path to do so except deleting and recreating the chore — the toggle is create-only, permanently, for the life of the chore.

Root cause, part 2 (no eligibility filter, create time). Even where the toggle IS wired (AddQuestModal), the assignment picker it's supposed to gate never enforces it. Compare AddQuestAssignSection.tsx:70's member filter — m.role === 'senior' ? inviteGrandparent : true — the exact "only show this role once its Welcome toggle is on" pattern EventFormModal's adults list uses for GP/Teen. There is no equivalent m.role === 'kid' ? teensOnly-aware-check : true anywhere in that filter chain (line 70-71): a kid (not teen) is offered as a directly-assignable member in the picker regardless of whether "Teens Only" is on, and toggling "Teens Only" on/off never clears an already-selected kid from assignIds the way turning on "Adult Task" clears kids (line 496) or turning on "Shopping" category clears kid/teen assignees (line 175-179). A parent can tap Teens Only on, then still hand-pick a kid directly in the very same form, producing a chore whose isOpenToTeens flag and actual assignee directly contradict each other with no warning — the exact "toggle doesn't clean up dependent state" bug class this pass's brief calls out, compounded by having no candidate-list filter to begin with (unlike the GP/Teen Welcome picker gaps already fixed in EventFormModal).

features/quests/components/EditQuestModal.tsx (no isOpenToTeens state, UI, or patch field anywhere in the file) — features/quests/components/AddQuestAssignSection.tsx:69-71 (member filter has a senior/GP-welcome check but no kid/teens-only check) — features/quests/components/AddQuestRecurrenceSection.tsx:103-117 (the Teens Only toggle itself — onPress={() => toggleTeensOnly(!teensOnly)}, no assignIds cleanup, unlike toggleAdultTask right above it in AddQuestModal.tsx:492-504) — store/choreAdapter.ts:419,600 and store/choreStore.ts:2019 (the write path already exists and would accept an edit-time patch if one were ever sent)

Medium 11 CategoryFields.tsx fields are create-only — no editable equivalent anywhere in EditEventModal, several with not even a read-only display

Root cause. Grepping every field name CategoryFields.tsx exposes against the full body of EditEventModal (features/calendar/EventFormModal.tsx from line 1546 on) turns up zero matches for: apptType (Medical appointment-type chips), sportType (Sports sport-type chips), kitReminder (Sports "pack gear" switch), isOnline/meetingUrl (Study online-session toggle + Zoom link), venueLocation (Sports venue / Study in-person location), clinicLocation (Medical clinic), generalLocation (Event/Birthday/Errand/Other location), and the entire linkGroceries/grocery-run attachment flow (Errand). Three of these — doctorName, coachName, subject — do at least get a READ-ONLY <Text> pill in the edit sheet's fixed detail-pills row (lines 2129-2143), so a parent can see but never correct them; the other 8 have no representation at all, not even for viewing. A parent who picks the wrong appointment type, forgets to mark a Study session online, or needs to fix a typo'd venue after creating the event has exactly one recovery path for any of these 11 fields: delete the event and recreate it from scratch. This confirms and substantially widens the prior Smart Tasker audit's "Doctor/Coach/Tutor/Clinic/Venue/Subject/Appointment-type/Sport-type are permanently un-editable" finding — Online/Meeting-link, Kit reminder, general Location, and the whole grocery-run attachment were not previously enumerated and are equally unreachable.

features/calendar/components/eventForm/CategoryFields.tsx:84-517 (every field listed above, create-form only) — features/calendar/EventFormModal.tsx:1546-2686 (EditEventModal's full body — confirmed via grep, zero matches for apptType/sportType/kitReminder/isOnline/meetingUrl/venueLocation/clinicLocation/ generalLocation/linkGroceries anywhere) — features/calendar/EventFormModal.tsx:2129-2143 (the 3 read-only display pills: doctorName, subject, coachName — view-only, no edit path)

Medium EditQuestModal's category chip row never merges in family custom categories — an existing custom-category chore can't be re-selected to its own category on edit

Root cause. AddQuestModal.tsx builds its category row from [...ALL_CATEGORIES, ...customCategories.filter(cc => !ALL_CATEGORIES.includes(cc.key))] (line 873) — the family's own custom categories (fetched via fetchCustomCategories, same mechanism EventFormModal uses) are merged in so a previously-typed custom category shows as a real, tappable chip. EditQuestModal.tsx never imports or calls fetchCustomCategories at all, and its category row (line 357-368) maps only ALL_CATEGORIES — the fixed 20-entry list from questFormShared.ts. A chore created under a family-specific custom category (something typed under "Other" that recordCustomSuggestion then promoted into a real category the family can reuse) opens in Edit with category state correctly seeded to that custom key, but no chip in the row ever highlights as active — the row silently shows nothing selected, and the only way to "keep" the original category is to close without touching the category row at all (since setCategory is never called unless a chip is tapped). Tapping any visible chip permanently replaces the custom category with a generic one, with no way back to the original short of retyping it in Add and hoping the family suggestion table still has it.

features/quests/components/EditQuestModal.tsx:355-368 (category row, ALL_CATEGORIES only, no customCategories fetch or merge) — features/quests/components/AddQuestModal.tsx:294-297,873 (fetchCustomCategories + merge, the pattern EditQuestModal is missing)

Medium A locked (claimed/in-progress) chore's "Adult-Only Task" toggle can still be flipped on, silently reassigning coins/visibility on an active chore with no confirmation

Root cause. EditQuestModal.tsx:591-614 renders the Adult-Only Task toggle unconditionally — "always visible so locked (Adjust) mode still shows the flags," per its own comment — with an onPress handler that unconditionally clears assignIds/isPool/ inviteGrandparent the instant it's flipped on (line 597), even when editMode === 'restricted' (a chore already claimed or in-progress by a kid). The locked save() patch branch (lines 155-184) does include isAdultTask/assignedToId/assignedToIds in its outgoing patch unconditionally — there's no extra confirmation step or warning distinct from the ordinary Alert.prompt that only fires on Delete. A parent editing a locked, in-progress kid chore for an unrelated reason (e.g. just extending the due date, though due date itself is excluded from the locked patch per the file's own comment) can accidentally tap this toggle, instantly wiping the kid's claim from assignIds in local state — the same "reassignment happens as a side effect of an unrelated edit" shape the EventFormModal helper-seeding bug (fixed via helperTouched) was designed to prevent, but with no analogous touched-flag guard here. This is speculative in severity (no live report cited), downgraded from High because the toggle requires a deliberate tap, not an automatic stale-diff — but the UI gives no distinct warning that flipping it mid-chore silently un-assigns an active kid.

features/quests/components/EditQuestModal.tsx:590-614 (Adult-Only toggle, unconditional assignIds/isPool/inviteGrandparent clear on press, rendered even when editMode==='restricted') — features/quests/components/EditQuestModal.tsx:145-184 (locked save() patch — sends the cleared assignment state with no distinct confirmation)

Medium Deleting one leg of a linked drop-off/pickup pair has no cleanup of the OTHER leg anywhere in the form layer — the orphan is a real, reachable gap

Root cause. handleDelete has no awareness of event.linkedLegId at all — it branches only on event.seriesId (recurring) vs. not, then hands off to the caller's onDelete. Deleting a drop-off leg that has a linked pickup leg (created via forkRideLegs either at creation or via "Needs pickup too?") leaves the sibling pickup event fully intact but now pointing at a linkedLegId that resolves to nothing — no confirmation dialog anywhere in this file asks "this ride also has a linked pickup, delete that too?" the way the recurring-series prompt asks about scope. This is a form-layer gap, not confirmed here as a live orphan in the underlying deleteEvent/deleteEventScoped store calls (out of this pass's file scope) — but nothing in EventFormModal itself surfaces the linked-leg relationship at delete time for a user to even make an informed choice, unlike the otherwise-thorough recurring-series prompt right next to it in the same function.

features/calendar/EventFormModal.tsx:2057-2083 (handleDelete — no linkedLegId branch or prompt) — features/calendar/EventFormModal.tsx:1723 (comment acknowledging linkedLegId exists and is used to SUPPRESS offering a second "Needs pickup too?" fork, but the same field is never consulted on delete)

Low Quest delete on a locked chore correctly requires a note; no equivalent "pending handoff" cleanup prompt exists, but this is out of this pass's form-layer scope

EditQuestModal.tsx:707-736's delete button correctly branches on locked (editMode==='restricted') to require a non-empty note via Alert.prompt before calling onDelete, and blocks the delete entirely if the note is empty (line 719) — a real, working guard. Whether a pending chore-handoff offer or GP-errand invite tied to this quest gets cleaned up server-side on delete is a choreStore/RPC-layer question the second QA pass (chore-handoff/bounty audit) already covers — no additional form-layer gap found here; the form itself has no separate "this has a pending handoff, are you sure?" branch, but nothing in this file's own state suggests one should exist beyond the note requirement already present.
