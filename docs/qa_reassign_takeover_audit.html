Reassign / Take-over Live QA Audit

A real, live QA pass against the FamilyCubeApp Supabase backend, exercised through the deployed qa-scratch-family edge function — real DB writes, real RPC calls under real minted sessions for 9 scratch family members (2 parents, 4 kids, 2 teens, 1 grandparent), verified by fresh independent read calls after every step. This follows two serious bugs found in the calendar reassignment system: a kiosk active-member propagation gap, and a forked ride-leg's stale driver_name/ helper_name pair winning over a fresh reassignment. This audit hunts for remaining gaps of the same shape — a field the write path forgot to touch, a read path that trusts the wrong field first, a client path that quietly diverges from the RPC everyone assumes it calls.

Scratch family used: 9919cb71-1a48-4202-953e-20237b068273 — created via setup, fully torn down via teardown at the end of this run (confirmed by a follow-up read on members returning zero rows for that family id). No other family's data was touched. Every RPC call in this document ran under a real minted session for the acting scratch member (magic-link + verifyOtp, exactly how the app's own recover-device flow works) — resolve_active_member_id() genuinely resolved via auth.uid() on every call, not a spoofed header.

Findings summary

9 scenarios run (the 8 requested plus one split-out from the take-over test to isolate the self-target confirm shortcut). 3 genuine bugs found, all confirmed against a live database, none fabricated or inferred from code alone.

High decline_event_assignment leaves driver_id/helper_id stale after a decline — regressed by a later migration

Root cause. Migration 20260930250000_assignment_rpcs_write_ids.sql correctly added driver_id = null / helper_id = null to decline_event_assignment's two branches, alongside the existing driver_name = null/helper_name = null. But the LATEST version of the function — 20260930360000_decline_event_never_closes_both_pools.sql, which is the one live in the database today — re-created the function to fix an unrelated bug (both pools staying closed after a decline) and, in doing so, dropped the driver_id/helper_id clears that the intervening migration had added. Its UPDATE statements only set driver_name = null, driver_status = null, ... and helper_name = null, helper_status = null, ... — the id columns are never mentioned, so Postgres leaves them exactly as they were. Confirmed live in §6 below: after Parent 1 declines a driver assignment, driver_name/driver_status read back null but driver_id still reads the declining member's own id. This is the exact bug class described in this audit's premise — a write path that clears the display field but leaves a stale id behind for a different read path to trust. Currently non-exploitable in the live UI only because every direct .driverId/.helperId consumer found in features/hub/*.tsx and hubComponents.tsx is gated behind the (correctly-nulled) name field first — but it is fragile: any new code that compares driverId/helperId to a viewer's own id without that gate (which is exactly what eventAssignee()'s own id field invites a caller to do) would silently attribute a declined ride back to the person who just declined it.

supabase/migrations/20260930360000_decline_event_never_closes_both_pools.sql (live version) vs. supabase/migrations/20260930250000_assignment_rpcs_write_ids.sql (the fix it regressed) — store/eventStore.ts:290-293 (eventAssignee, the one safe consumer pattern) — features/hub/ParentView.tsx:210-217 (a consumer that relies on the staleness on purpose, see note in §6)

Critical The live "Claim" button never calls claim_pool_quest — a separate, unauthenticated client write path handles every real pool-chore claim

Root cause. The harness (and this audit's Scenario 5) exercises the Postgres RPC claim_pool_quest(p_chore_id, p_member_id), which correctly calls resolve_active_member_id() and rejects any caller whose real session doesn't match p_member_id. But that RPC is not what the app's own live "Claim"/"Take It" button calls. store/choreAdapter.ts:368's claimQuest — itself described in its own comment as "the only reachable Claim action in the live app (KidView, TeenView, QuestsScreen)" — calls store.claimPoolQuest(id, memberId, onLost), a different, same-named store method (store/choreStore.ts:2496-2530) that issues a raw supabase.from('chore_tasks').update({...}).eq('id', choreId).is('assigned_to_id', null) — no RPC, no resolve_active_member_id() check at all. The client-side CAS (.is('assigned_to_id', null)) does prevent two different claimants from both winning the same chore, but it never verifies the caller genuinely is the member id it's about to write into assigned_to_id — any client that can reach this code path (or replay the same REST call with a different memberId in the body) can claim a chore as any other family member, something the RPC of the identical name was specifically built to prevent. It also means claimed_at is set by this path (line ~2503) but never by the server RPC — the two "same name, different code" paths don't even agree on side effects, exactly the deceptive split-behavior shape described in this audit's premise (kiosk active-member bug). Live-confirmed in §5: calling the actual claim_pool_quest RPC as Kid 3 left claimed_at = null in the row, which deriveCardActions.ts:132-141's own comment says should only ever happen via a real pool self-claim — meaning the RPC path and the UI's documented behavioral assumption ("claimedAt is only ever set by claimPoolQuest") are already inconsistent with each other, regardless of which path fires.

store/choreAdapter.ts:356-368 — store/choreStore.ts:2496-2530 (claimPoolQuest, the actual live path) — supabase/migrations/…claim_pool_quest (the unused-by-the-UI, actually-authenticated RPC) — features/tasks/lib/deriveCardActions.ts:132-141 (canGiveBack's claimedAt assumption)

Medium reassign_event auto-confirms a "take-over" of someone else's already-confirmed slot instead of leaving it pending

Root cause. reassign_event's status rule is purely v_status := case when p_new_member_id = p_actor_id then 'confirmed' else 'pending' end; — it has no notion of "am I overriding someone else's existing confirmed assignment" vs. "I'm accepting a fresh open slot." deriveCardActions.ts's showOverride (line 272, helperConfirmed && !isSelfAssigned) is presented in the UI as a distinct, heavier action from a plain reassign — implying some extra confirmation step — but the RPC underneath treats an override exactly like a normal self-assign: instant confirmed, no pending window, no signal to the person being overridden that a decision was potentially still in flight when it was silently replaced. Confirmed live in §8/§2.4: Parent 2 confirms as driver; Parent 1 calls reassign_event targeting themself; the row goes straight to driver_status = 'confirmed' with no intermediate pending state, in the same transaction, no different from a first-time claim. This may be intended product behavior for a same-role override (a parent overriding a parent), but the RPC gives the UI no way to distinguish "I'm claiming an open slot" from "I'm bumping someone who already committed," which is exactly the ambiguity a showOverride-specific code path in the UI implies should exist.

supabase/migrations/20260940020000_reassign_event_clears_other_assignee_pair.sql:73 (v_status assignment, unchanged from the original reassign_event logic) — features/tasks/lib/deriveCardActions.ts:270-272 (showReassign/showOverride distinction the RPC doesn't honor)

4 · Recurring series confirm forward-sweep STATIC ONLY

Harness limitations encountered

  • add_event's insert only accepts {'{'}familyId, memberId, category, title, date, time, rideRequired, driverName, driverId, helperName, helperId{'}'} — no way to set linked_leg_id, series_id, is_series_anchor, or recurrence_rule. Scenario 2's true fork-leg linkage and Scenario 4's recurring series had to be approximated (2) or verified statically (4) as a result. Both are noted explicitly at the point they occur above rather than silently asserted as fully live.
  • add_quest only accepts {'{'}familyId, title, isPool, assignedToId, status{'}'} — no way to set inviteGrandparents/isOpenToTeens gating flags on a chore, so the GP/teen-eligibility half of Scenario 5's pool visibility check is static-only.
  • All other RPCs tested (assign_event_role, reassign_event, confirm_event_assignment, decline_event_assignment, claim_event_slot, claim_pool_quest, submit_chore, approve_chore) worked exactly as documented in the harness header, with no errors beyond the one expected/correct rejection in step 6.1a.
