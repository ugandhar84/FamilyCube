Smart Task Composer — Detection Quality & Create→Edit Audit

A third QA pass on FamilyCubeApp, scoped to the local "just describe it" quick-add parser (features/tasks/lib/localTaskDetection.ts) and its composer UI (features/tasks/components/SmartTaskComposer.tsx) — not the reassign/claim RPC territory two other in-flight passes already cover. This follows a just-fixed bug (commit 64022f5f): typing a both-ways ride in one sentence silently dropped the second (return/pickup) time, with the only manual fallback UI gated behind a location field that never populated for a named-venue phrasing. Every extraction result below was produced by executing the REAL exported functions from localTaskDetection.ts (copied verbatim, only its @/lib/dates import rewired to a same-file shim of localDateStr) via npx tsx — not a reimplementation, not a prediction from reading the regex.

Method. 7 realistic, deliberately-ambiguous sentences (one or more per category) run through the real detectLocalTask/extractDateTime/extractLocations/extractAmount/ extractDriver/extractPerson/extractMemberNames exports, output captured verbatim below. No live DB writes were needed for this pass — this is detection/UI-logic territory, not RPC identity — so the qa-scratch-family harness wasn't used. The composer UI (SmartTaskComposer.tsx) and full edit forms (CategoryFields.tsx, EventFormModal.tsx's EditEventModal, EditQuestModal.tsx) were read in full to determine, for each dropped detail, whether ANY manual field exists anywhere in the app to add it back.

Findings summary

7 hand-crafted sentences, one per requested category (Ride got the requested extra third-party-return variant). Every one of them lost at least one real, correctly-stated detail. Two gaps have literally no field anywhere in the app to recover the lost information (High); four have a workaround only in the full form, undiscoverable from the quick composer (Medium); three have a working manual fallback in the composer itself (Low).

High A second doctor+date in the same sentence is completely and silently discarded — no field anywhere captures it

Root cause. extractDateTime's date-word regexes (day after tomorrow / today / tomorrow / extractDayOfWeek) each only ever match the FIRST occurrence in the sentence — exactly the same "no /g/ flag, first-match-wins" shape as the just-fixed return-time bug, except here it's the DATE field, not a bolted-on second time field. For "…next Tuesday at 3pm, then a follow-up with Dr. Chen the week after," extractDayOfWeek resolves once to Tuesday (matched against "next Tuesday"), and there is no regex anywhere in the file that recognizes "the week after" as a second, later, RELATIVE date — it isn't a weekday name, "tomorrow," or "day after tomorrow," so it silently produces nothing. The second doctor name (Dr. Chen) is never extracted at all — localTaskDetection.ts has no doctor/coach/tutor-name extraction function of any kind; those fields exist purely as SmartTaskComposer TextInputs the user fills by hand. Confirmed live: detectLocalTask on this sentence returns when: {date: "2026-09-15", time: "15:00"} (only the first appointment) and a title truncated to "Emma has a dentist appointment with Dr. Patel" — Dr. Chen's follow-up leaves zero trace in any field. Because the composer is single-event-per-submission by design, there is genuinely no field anywhere in the quick-add flow OR the full EventFormModal that can hold "a second, different appointment" — a parent who dictates this exact common two-appointment sentence gets one correct event and one silently vanished one, with no error, warning, or "wasn't totally clear" banner (confidence reads 95%, the detector's own most-confident tier).

features/tasks/lib/localTaskDetection.ts:277-293 (extractDayOfWeek, single-match) — features/tasks/lib/localTaskDetection.ts:313-343 (extractDateTime, no second-date support outside the Ride-specific returnTime carve-out) — features/tasks/components/SmartTaskComposer.tsx (single addEvent() call per submission, no multi-event support)

High A second tutor+day+time pairing is silently dropped with the sentence still reading as high-confidence and error-free

Root cause. Same shape as the medical finding above, but worse: for "Math tutoring with Ms. Rao on Mondays at 4, and Wednesdays with Mr. Lee at 4:30," the ENTIRE when block comes back {date: null, time: null} — confirmed live. Neither "Mondays" nor "Wednesdays" match extractDayOfWeek's day-name regexes (they require the bare/near-bare weekday token; the plural "Mondays" still matches the substring "monday" via \bmonday\b... but the recurrence block (a SEPARATE code path, see Sports finding below) is what actually reads plural/weekday tokens for recurrence, and extractDayOfWeek here is gated behind the non-recurring one-shot date path, which this sentence never reaches because "weekly"/"every" isn't present, so recurrence stays 'once' AND the date fields stay null). "Ms. Rao" and "Mr. Lee" are both completely invisible to the detector — there is no tutor-name extraction function, and the sentence never contains a known family-member first name, so extractMemberNames/extractPerson also return nothing. Confirmed: category correctly resolves to school/Study (82% confidence — a real "wasn't totally clear" banner does NOT show, since that only fires at confidence 0), title reads "Math tutoring with Ms. Rao on Mondays" (Mr. Lee's Wednesday session isn't even in the truncated title). This is fundamentally NOT representable as a single event — two tutors, two days, two times, one subject — and the app has no multi-occurrence-per-sentence handling anywhere; the second tutor/day/time is not merely hard to reach, it never lands in the app's data model in any form, silently.

features/tasks/lib/localTaskDetection.ts:277-293, 640-651 (recurrence day-token matching is a separate code path from the one-shot date path, and this sentence satisfies neither cleanly) — features/tasks/lib/localTaskDetection.ts (no extractTutorName/extractCoachName/extractDoctorName function exists at all) — features/calendar/components/eventForm/CategoryFields.tsx:171-175 (Study's single tutorName TextInput — one tutor per event, by construction)

Medium A third-party return leg ("grandma... bring him back") resolves to nothing — no driver, no return time, no location for the return

Root cause. For "Pick up Jack from school at 3:15 and drop at grandma's, she'll bring him back by 7" — confirmed live: when: {date: null, time: null, returnTime: null} (the bare "3:15"/"7" have no am/pm suffix, and extractDateTime's time regex REQUIRES an am/pm token — /\b(\d{1,2})(?::(\d{2}))?\s?(am|pm)\b/i — so both clock times are silently dropped purely because the parent didn't say "pm," a very natural omission when the context makes it obvious). locations.pickup correctly resolves to "School" (a genuine PASS — PICKUP_CONTEXT_RE correctly finds "from school"). extractDriver returns null — it only recognizes an ADULT family member matched by first name against explicit driver-phrasing regexes ("the driver should be X," "driven by X," "X should drive"); "grandma's" (a location, not a name) and "she" (a pronoun) match neither pattern nor any member's first name, so the entire third-party-return concept — a DIFFERENT person than whoever the ride is nominally "for" doing the return leg — is invisible to the detector. Worse: this sentence's own composer flow assumes ONE driver field (helperId) for the WHOLE ride, with no concept of "driver for the drop-off" vs. "driver for the return" as distinct people — even manually, a parent cannot record "Grandma does the return leg" anywhere in the Ride category's fields (pickupLocation/dropLocation/returnTime/helperId is one undifferentiated driver for the entire round trip). The closest workaround is typing "Grandma" into the free-text Drop-off location field or the collapsed Notes box, neither of which is a real driver assignment.

features/tasks/lib/localTaskDetection.ts:335 (time regex requires am/pm, no bare-hour fallback) — features/tasks/lib/localTaskDetection.ts:412-427 (extractDriver, single first-name/adult-only match, no third-party/pronoun handling) — features/calendar/components/eventForm/CategoryFields.tsx:280-336 (Ride fields: one driverId for the whole round trip, no separate return-leg driver anywhere, quick composer or full form)

Medium RSVP deadline and "no gifts please" both vanish — RSVP has no field anywhere in the app; "no gifts" only reachable via collapsed Notes

Root cause. For "Mia's birthday party Saturday 2-4pm at Chuck E Cheese, RSVP by Wednesday, no gifts please" — confirmed live: category correctly resolves Birthday (95% confidence), date/time correctly resolve to Saturday 4pm (the SECOND clock time in "2-4pm" wins, since the time regex isn't anchored to the first number in a range — worth noting as accidentally-correct behavior, not a deliberate range parser: a sentence like "9-10am" would keep the LAST match too, which is usually but not always the desired one). locations comes back null/null — "Chuck E Cheese" is never captured anywhere; Birthday's only location field in CategoryFields.tsx is generalLocation, which the composer does expose (line 970, "Location (optional)") — so this one has a real fallback, just requires the parent to notice the venue was dropped from the auto-detected fields and manually retype it. "No gifts please" has the same fate — no dedicated field, Notes-only, Notes collapsed by default.

Medium Two distinct errands in one sentence get merged into a single miscategorized chore titled with both tasks run together

Root cause. For "Pick up dry cleaning and drop off library books, need to do both before 5pm today" — confirmed live: category resolves to Laundry (95% confidence, questCategory: 'Laundry'), not Errand — "dry cleaning" is a Laundry keyword (2-word phrase match, weight 6) and beats "library" (an Errand keyword, single word, lower weight), so the SECOND errand (library books) doesn't just fail to get its own task — it actively mis-steers the category of the ONE task that does get created. The title is truncated to "Pick up dry cleaning and drop off library books, need to do both be…" (the cutoff regex only strips trailing date/time/urgency tokens, not the mid-sentence "and" splitting two independent tasks), so the library errand is technically still visible as text inside the title, but nowhere as a structured, separately trackable/completable task. The app has zero multi-item/multi-task detection anywhere in detectLocalTask — it is fundamentally a single-category, single-title, single-date-time function with no sentence-splitting logic. A parent who dictates two real errands in one breath — a very natural way to talk — gets one chore, wrongly categorized, with a run-on title, and the app gives no signal ("wasn't totally clear") that anything was collapsed since confidence reads 95%, its most confident tier.

features/tasks/lib/localTaskDetection.ts:566-669 (detectLocalTask: single title, single category, single when — no sentence-splitting or multi-task output type exists) — features/tasks/lib/localTaskDetection.ts:80-85 vs 104-108 (errand vs. laundry keyword weight collision: "dry cleaning" is filed under laundry's kw list, not errand's, so an errand sentence that happens to mention dry cleaning is silently re-categorized)

Low extractAmount correctly isolates $45 from a sentence with two other bare numbers, but the title still gets truncated mid-sentence

Root cause. For "Pay the babysitter $45 for Friday night, she watches the kids from 6 to 11" — confirmed live: extractAmount correctly returns exactly 45 — the $-anchored regex (/\$\s?(\d+(?:\.\d{1,2})?)/) can't accidentally match the bare "6" or "11" since neither has a dollar sign or "dollars/bucks" suffix; this is a genuine PASS, and the amount correctly lands in the composer's Coins field (repurposed for a payment amount here, same shared coinsStr field). The more interesting silent-drop is elsewhere: extractLocations's bare "from X to Y" pattern (line 393, with NO required ride-context verb before it, unlike the guarded "from" fallback documented in that file's own comment) spuriously matches "from 6 to 11" and sets locations.pickup = "6", locations.dropoff = "11" — confirmed live. This is harmless in THIS case only because category resolves to general_task (confidence 0, no keywords hit), so the Ride-only pickup/dropoff UI never renders and these garbage values are invisible — but it demonstrates the exact "from X to Y" pattern the file's own PICKUP_CONTEXT_RE comment says was already tightened once for a near-identical false-positive ("I'm in the living room" matching an unrelated "from"). The unconditional from X to Y regex at line 393 was never given the same scoping. Also silently dropped: "she watches the kids from 6 to 11" (the actual work-hours context) has no field anywhere — Notes-only, collapsed by default, same as prior findings.

features/tasks/lib/localTaskDetection.ts:471-476 (extractAmount, correct) — features/tasks/lib/localTaskDetection.ts:391-397 (unconditional bare "from X to Y" match, unlike the scoped PICKUP_CONTEXT_RE right below it) — currently non-exploitable in the UI only because general_task never renders Ride fields, same fragility pattern as the reassign audit's Finding #1 (a latent bad value that happens to be gated off today by an unrelated check)

Low Sports' two-weekday recurrence detection is a genuine PASS — flagged here only to document it against the audit's premise

Included for completeness per the audit's Scenario 2 ask: recurrenceDays correctly returns [2, 4] (Tuesday + Thursday) for "every Tuesday and Thursday at 5pm" — the day-token forEach loop at line 648 tests every token in DAY_TOKEN_MAP against the input independently and pushes every match, so this is NOT subject to the same "first-match-only" bug class as extractDayOfWeek/the pre-fix time regex. No manual-fallback question applies since nothing was dropped.
