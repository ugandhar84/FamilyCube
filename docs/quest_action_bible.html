1 · The two systems, in one paragraph each

System A — parent_quest_assignments table, ParentQuestAssignment type in store/choreStore.ts:171. Parent-to-parent negotiation only. States: PENDING → ACCEPTED/IN_PROGRESS → COMPLETED, or PENDING → PARKED (unlocked, bounce 1) → PARKED (locked, bounce 2) → reassigned/reopened, or PENDING → DECLINED, or PENDING → SNOOZED → PENDING. The underlying chore_tasks row stays unassigned (assigned_to_id = null) until the assignment is ACCEPTED — this is deliberate (addParentQuest, store/choreStore.ts:1606-1614) so the assignee's Accept/Respond card actually renders instead of the chore looking pre-claimed.

System B — plain chore_tasks.assigned_to_id + chore_tasks.status, no accept step. Covers kid/teen chores, bounty pool, citizenship/routine, GP-sponsored quests (grandparent_quest, both the parent-safety-review gate and the GP-verification step), shopping quests, and GP-welcome/invited errands (openToGP). Whenever a task is directly assigned by a parent to another parent/senior (not System A DIRECT mode, not System B claim-by-kid), it also lands here as a plain assignedToId write once accepted.

The two systems interlock through getActiveAssignmentChoreIds() (store/choreStore.ts:2077-2082) — the single source of truth for "does this chore have a live System-A negotiation happening." Every write path that could otherwise silently steal a chore out from under a pending assignment (Take It, auto-assign, Edit's reassign picker) must check this set first. This was gap #1 from an earlier audit pass in this same session; it is now consulted in ParentView.tsx:282-295 (Household Backlog pool) and QuestsScreen.tsx:424-429 (Chores tab pool) — both screens read the identical selector, so they cannot drift apart on this point. Verified fixed in all branches below (see Scenario 5).

5 · Scenario 3 — Co-parent snoozes 48h

Actors: Priya (assigner), Marcus (assignee, snoozes).

Marcus → Respond → Snooze 48h → respondToParentQuest(a.id, {action:'SNOOZE'}).
Writes: assignment → SNOOZED, snoozeUntil = now + 48h. Chore row untouched.
During the snooze window — Marcus's screen: nothing at all. getMyDirectPending's filter (choreStore.ts:2084-2092) explicitly excludes SNOOZED assignments whose snoozeUntil is still in the future — the task is invisible to him until it expires.
During the window — Priya's screen: OutgoingPendingCard stays visible, label "Snoozed by Marcus — waiting" (OutgoingPendingCard.tsx:38-39). No action available to her either — genuinely just a wait state.
48 hours pass (no explicit "un-snooze" action exists anywhere in the codebase — this was checked specifically; there is no button, only time).
Marcus's screen: the assignment reappears in getMyDirectPending automatically the next time the selector runs (any store re-render/data refresh) once snoozeUntil <= now — back to a normal DirectPendingCard with Accept/Respond.
Priya's screen: label switches from "Snoozed — waiting" back to plain "Waiting on Marcus to accept" (the isBounced/isSnoozed ternary in OutgoingPendingCard.tsx:35-40 re-evaluates against current time on each render).
Early un-snooze: not possible through any UI action found — the assignee cannot manually end their own snooze early; declining or waiting out the clock are the only two paths.

6 · Scenario 4 — Two-bounce pushback → lock → reassign

Actors: Priya (assigner), Marcus (assignee), then Alex (third parent, reassign target).

Marcus → Respond → Blocker (or Trade/Discuss — all three share this branch) → respondToParentQuest(a.id, {action:'BLOCKER', details:'Car is in the shop'}).
Writes: assignment → PARKED, bounceCount:1, isLocked:false (bounce 1 stays unlocked — choreStore.ts:1656-1665). Chore → unassigned, status:'todo'.
Marcus's screen: still renders as DirectPendingCard (still in getMyDirectPending's PARKED branch, choreStore.ts:2089) — the pushback text shows inline ("Bounced: ..."), and Accept/Respond are still both available, so Marcus himself could still bounce it a second time or accept it.
Priya's screen: flips to OutgoingPendingCard with "Marcus pushed back — waiting on your response," pushback details shown italic. Confirmed dead end — this card has no button of any kind (verified: no Pressable/TouchableOpacity anywhere in OutgoingPendingCard.tsx besides the expand/collapse chevron). Priya, the person the pushback is actually addressed to, cannot respond to it from this card. Her only path forward is to wait for Marcus to either accept it himself or bounce it a second time (locking it), or to independently open DelegateSheet from elsewhere and reassign the underlying chore, which would create a fresh assignment and — per addParentQuest's stale-assignment cleanup — force-close this PARKED one to COMPLETED. This is a real usability gap, though not a data-integrity bug (nothing breaks; there's just no direct reply button on the assigner's own card).
Marcus bounces a second time (any of Blocker/Trade/Discuss again) → respondToParentQuest called again on the same assignment.
Writes: bounceCount:2 → isLocked:true (two-bounce rule, choreStore.ts:1662-1664).
Both Marcus's and Priya's screens: LockedAssignmentCard — "Discuss offline with [other party] — bounced," Reassign + Reopen buttons, sourced from getMyLockedItems which explicitly includes both assignedTo === memberId and assignedBy === memberId (choreStore.ts:2098-2103) — this was itself an earlier-session fix (previously only the assignee could see a locked item).
Priya taps Reassign on her LockedAssignmentCard → opens DelegateSheet, picks Alex → addParentQuest(choreId, Priya.id, Alex.id, 'DIRECT', note).
Writes: addParentQuest's stale-assignment sweep (choreStore.ts:1548-1562) finds the still-open (locked, non-terminal) PARKED assignment on this chore and force-closes it to COMPLETED — not DECLINED, which is a slightly odd terminal label for something that was actually abandoned/reassigned, but it is at least terminal so it stops showing anywhere. New assignment row created, PENDING, assignedTo=Alex.
Alex's screen: gains a fresh DirectPendingCard, exactly like Scenario 1's starting state.
Priya's screen: her LockedAssignmentCard is replaced by a new OutgoingPendingCard for the Alex assignment.
Marcus's screen — the ORIGINAL assignee: Confirmed confusing gap. His LockedAssignmentCard simply vanishes (the assignment he was party to is now COMPLETED, a terminal status excluded from getMyLockedItems). No message, no "this was reassigned to Alex" notice. From Marcus's point of view the task he was mid-negotiation on just silently disappeared with zero explanation. Confirmed by reading every write path in addParentQuest and DelegateSheet.tsx — no chat/notification call exists anywhere in this flow.
Alternative ending: Priya taps Reopen instead → cancelLockedAssignment(a.id).
Writes: assignment → DECLINED, isLocked:false.
Both Priya's and Marcus's screens: LockedAssignmentCard disappears for both. Chore reappears as an open PoolQuestCard for anyone (see Scenario 5 for who can now act on it).
Same "silent disappearance, no explanation" issue applies to Marcus here too.

9 · Scenario 7 — Teen assigned a chore directly, declines

Actors: Priya (parent), Jordan (16, teen, assignee).

Priya directly assigns "Clean the garage" to Jordan (a plain System-B assignment, not System A — assignedToId set directly, since this is a household chore not an adult-only task).
Jordan's screen — Chores tab: QuestCard.tsx renders with canKidDecline = isKidOrTeen && isTodoCard && !q.isPool && ... (QuestCard.tsx:87) — true for a teen. Button label "Can't do this" (QuestCard.tsx:719) is present and tappable.

14 · New bugs found & fixed this pass

Four issues were found while tracing the scenarios above and fixed in the same pass (npx tsc --noEmit confirmed 0 errors after all four). These are in addition to the two fixes ("T1" and "G2") already recorded in the prior audit pass and its doc.

Fixed B1 — Teen declining a GP-sponsored quest on the Chores tab silently did nothing

features/quests/QuestsScreen.tsx — handleDeclineConfirm, line ~623

Scenario: Jordan (16, teen) is assigned a grandparent-sponsored quest at status:'todo'. He taps "Decline" (rendered because canAcceptGp/canKidDecline in QuestCard.tsx were both correctly widened to isKidOrTeen in the prior "T1" fix). The confirm handler's GP-routing branch checked isKid, not isKidOrTeen — so a teen fell through to the generic else branch, which calls declineQuest → store.requestRedo, a function guarded to only fire on status === 'pending_approval'. The chore was still at todo. The call silently no-op'd: sheet closed, no error, chore unchanged, sponsor never notified, nothing released to the pool.

Fix: changed the branch condition from isKid to isKidOrTeen, matching the gate that renders the button in the first place.

Fixed B2 — "Can't do this" on a plain assigned household chore (Chores tab) silently did nothing, for both kids and teens

features/quests/QuestsScreen.tsx — handleDeclineConfirm, line ~646

Scenario: the primary, most common decline path — a kid or teen assigned an ordinary household chore (not GP, not a multi-participant row) taps "Can't do this" (canKidDecline, QuestCard.tsx:714-721) at status:'todo'. The confirm handler's fallback branch unconditionally called declineQuest(id, ..., reason, 'custom') → requestRedo, the same pending_approval-only guard as B1. Same silent no-op: the earlier "T1" fix (widening isKid→isKidOrTeen so the button rendered for teens too) never verified the underlying action actually worked for either role at this status — it only fixed visibility of a broken button, not the break itself.

Fix: added a branch — when the target is a kid/teen and the chore's status is not pending_approval (i.e. this is a pre-submission "can't do this," not a parent declining a submission), route through reassignQuest(id, '', by) instead — the same "send back to the pool" mechanism the multi-participant row's own inline "Can't do this" button already used successfully. A parent/senior declining an actual pending_approval submission still goes through requestRedo as before, unaffected.

Fixed B3 — reassignQuest('', ...) wrote an empty string to assigned_to_id instead of NULL

store/choreAdapter.ts — reassignQuest, both the hook and the static .getState() implementations

Found while fixing B2 — the "send back to pool" call this pass now depends on (reassignQuest(id, '', by), already used elsewhere for participant-row declines) passed '' straight through to updateChore({assignedToId: memberId}). updateChore's DB patch only writes NULL on a nullish value (updates.assignedToId ?? null) — an empty string is not nullish, so the chore's assigned_to_id column would end up literally '' rather than actually open/unassigned, and isPool was never set either, so the chore would not correctly reappear as a claimable pool item.

Fix: both reassignQuest implementations now write assignedToId: memberId || undefined (so '' maps to undefined → DB NULL) and set isPool: memberId ? undefined : true so an unassign genuinely reopens the chore to the pool.

Fixed B4 — Hub had no decline button at all for a plain assigned household chore (kid or teen), only the Chores tab did

features/hub/kid/KidQuestCard.tsx, features/hub/kid/DeclineQuestSheet.tsx

Scenario: the earlier "T1" fix from the prior audit pass was scoped to QuestCard.tsx (the Chores tab) only. The Hub's own kid/teen card, KidQuestCard.tsx (shared by both KidView and TeenView via MyQuestsSection), only ever rendered a Decline button inside its isGpTodo branch — a plain non-GP assigned chore at todo/in_progress got exactly one button, "Mark Done → Get Paid," with no escape hatch. A kid or teen who genuinely can't do an assigned chore had a decline option on the Chores tab but not on the Hub — a real Hub-vs-Chores-tab divergence, exactly the class of bug this document was asked to hunt for.

Fix: added canDeclinePlain (todo/in_progress/claimed, not pool, not GP) to KidQuestCard.tsx, rendering a paired "Mark Done" + "Can't do this" button row, wired to the existing onDeclineGpQuest callback (reused, not a new prop — see below). DeclineQuestSheet.tsx's submit handler now branches on the target chore's own categoryType: grandparent_quest still calls declineGrandparentQuest exactly as before; any other category now calls updateChore(id, {assignedToId:undefined, isPool:true, status:'todo'}) directly (the Hub has no reassignQuest action threaded down to this depth, so this mirrors what that action now does post-B3) plus a chat message to the family channel. Both KidView.tsx and TeenView.tsx wire this same sheet/card pair identically, so the fix covers both roles without any changes needed in either view file.

15 · Known gaps — flagged, not fixed this pass

Real, code-confirmed gaps that were judged out of scope for a targeted bug-fix pass (larger design decisions, or requiring schema/edge-function changes not verifiable from the client alone). Listed so they're not silently lost.

Gap System A never notifies the assigner of DECLINE, a completed hand-off, or an ACCEPT

Confirmed by reading respondToParentQuest and completeParentQuest in full — neither calls sendMessage nor quest-event-notifier anywhere. Priya (the assigner) only ever learns Marcus declined, accepted, or finished a task by noticing the card is gone/changed the next time she happens to open Household Backlog or the Chores tab. cheerChore and appreciationPing both call the notifier edge function; the core System-A transitions do not, an inconsistency worth a deliberate product decision rather than a blind fix.

Gap A first-bounce pushback (PARKED, unlocked) gives the assigner no reply button

OutgoingPendingCard.tsx is genuinely read-only — no Pressable wired to any store action besides its own expand/collapse chevron. The assigner can see the pushback text but cannot respond to it directly from that card; their only paths are to wait for the assignee to bounce again (locking it) or accept it, or to independently delegate elsewhere (which force-closes the PARKED assignment as a side effect of addParentQuest's stale-assignment sweep, not as a designed "respond to pushback" flow).

Gap The original assignee gets no explanation when a locked assignment is reassigned or reopened out from under them

Confirmed in both DelegateSheet.tsx and cancelLockedAssignment — neither fires any chat/notification call. Marcus's LockedAssignmentCard simply disappears once Priya reassigns to Alex or reopens to the pool; from his side, a task he was mid-negotiation on vanishes with zero explanation.

Gap Multi-select assignment in the standard Add Quest form silently degrades to single-assign

createParticipants is a no-op stub in choreAdapter.ts, and the underlying addChore call only ever persists the first id from a multi-select (assignedToId ?? assignedToIds?.[0]). Selecting Alex and Jamie both in AddQuestModal assigns the whole quest to whichever kid happened to be first in the array — Jamie gets nothing, sees nothing, and there is no participant row for her at all. This is a real, currently-reachable data-loss-adjacent gap (not merely a dead button) and the highest-priority item in this list for an actual fix, but implementing it correctly (participant rows vs. team-clone rows, and reconciling with the currently-dead approveParticipant/declineParticipant/reopenParticipant stubs) is a design decision beyond the scope of this documentation-plus-targeted-bugfix pass.

Gap approveParticipant / declineParticipant / reopenParticipant are dead stubs behind a live UI

QuestCard.tsx's per-participant action row (Approve/Decline/Reopen, lines 594-617) renders and is tappable whenever a quest has >1 participant, but all three underlying calls are no-op async functions in choreAdapter.ts. In practice this UI is rarely reached today because of the multi-assign gap above (there's currently no reliable way to end up with a genuine >1-participant quest through the standard form), but it is real dead UI that would silently fail to do anything the moment it becomes reachable.

Gap openToGP vs. inviteGrandparents — two different booleans with overlapping intent, not verified to be kept in sync

The shopping/errand-specific "Offer to GP" toggle (PoolQuestCard.tsx, OthersAdultQuestCard.tsx, DelegateSheet.tsx) writes chore.openToGP. claimGPErrand's own guard, and the Chores tab's senior-role visibility filter (QuestsScreen.tsx:466-472), both check chore.inviteGrandparents instead — a separate field set by a different UI (EditQuestModal/AddQuestModal's "Invite Grandparents?" toggle). No code path was found in this pass that sets both fields together from the openToGP-specific toggles. This was not runtime-tested (no simulator access in this session), so it is flagged as a likely-but-unconfirmed gap rather than asserted as a certain bug.

Gap declineGrandparentQuest's sponsor notification is caller-provided, not guaranteed by the store action

The store action itself sends no chat message — every current caller (DeclineQuestSheet.tsx, QuestsScreen.tsx) happens to separately call sendMessage right after, but nothing enforces this. A future caller of declineGrandparentQuest that forgets the follow-up message would silently decline the quest with zero notification to the sponsor, and there would be no compiler or runtime signal that anything was missed.
