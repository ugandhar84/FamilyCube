Findings

Fixed T1 — Teens have no way to decline a directly-assigned household chore

features/quests/components/QuestCard.tsx:76 · features/hub/kid/KidQuestCard.tsx (isActionable branch)

Scenario: Priya (parent) assigns "Clean the garage" directly to Marcus (16, teen). Marcus is swamped with finals and genuinely cannot do it this week. In QuestCard.tsx, canKidDecline = isKid && ... — teens are explicitly excluded ("teens CANNOT decline (no decline authority)" per the comment). But that comment describes GP-quest accept/decline symmetry, not household chores. Marcus has no button at all — his only path is to submit garbage work or silently ignore it, both bad outcomes for a genuinely legitimate case (he does not "have no decline authority" in the way a toddler getting a chore might — he is old enough to negotiate, closer to an adult).

Root cause: The comment's intent (teens don't get parent-to-parent-style negotiation) got over-applied to block ALL decline, including the same one-tap "Can't do this → back to pool" flow kids already have. That's not a two-bounce negotiation — it's the same flat decline a kid gets. There is no reason a teen should have strictly fewer options than a kid here.

Fix: Teens get the exact same one-tap decline-to-pool flow kids already have (not the full parent pushback system — that stays parent-only, consistent with judgment below on G-negotiation). Changed the gating from isKid to isKidOrTeen in QuestCard.tsx's canKidDecline, and in KidQuestCard.tsx/MyQuestsSection wiring (teens already share the same component tree as kids for quest cards, so this was a one-line gate fix, not new UI).

Not a gap G1 — A GP-approved bounty targeted at 2+ kids showing wrong claim state to siblings

store/choreStore.ts:1225-1256 (approveGrandparentQuestAsParent) · features/hub/kid/KidQuestCard.tsx

Scenario checked: Grandpa sponsors "Rake the whole yard" for both Alex and Jamie (siblings). Once a parent approves, the store clones the chore — each kid gets their own todo row with the SAME teamGroupId and targetChildIds. Alex claims and starts his clone. Jamie opens the Chores tab: her own clone is untouched (still todo, unclaimed) so she correctly sees her own claim button.

Disposition: Verified OK — the team-clone design (independent chore id per kid, linked only by teamGroupId for display) already prevents cross-contamination. No code change needed.

Fixed G2 — A parent has no way to review/redo a GP-sponsored quest sitting in pending_grandparent_approval if the sponsor GP is unavailable

store/choreStore.ts:1175-1187 (requestGrandparentRedo) · features/hub/parent/ChoreReviewSection.tsx

Scenario: Grandma sponsors "Call and tell me about your school day" (virtual quest) for Priya's daughter Zoe. Zoe submits proof. Grandma is traveling and doesn't open the app for 3 days. Meanwhile Priya (the parent) opens Chore Reviews — ChoreReviewSection only surfaced gpPending (pending_parent_approval) and gpDeclined quests. A quest sitting in pending_grandparent_approval — submitted, waiting on the grandparent's OK — was completely invisible to the parent. Priya couldn't approve it herself, couldn't nudge, couldn't do anything; Zoe just waited indefinitely with no parent-side visibility into a stuck review.

Fix: Added a "Grandparent Quests — Awaiting Grandparent Review" sub-section to ChoreReviewSection.tsx listing chores in pending_grandparent_approval, showing sponsor name and submitted-at, with a "Nudge grandparent" action (chat DM to sponsor) and a parent-side fallback Approve & Pay using the same payout path as grandparentApproveAndCheer, so work doesn't sit blocked indefinitely if the GP is unreachable. Mirrors the existing GpSafetyReviewCard/GpTurnedDownCard pattern already in that file.

Not a gap G3 — Team-clone GP quest decline notification

features/hub/kid/DeclineQuestSheet.tsx:83-94 · store/choreStore.ts:1810-1832 (declineGrandparentQuest)

Scenario checked: A 2-kid team GP quest clone is declined by one sibling. Does the sponsor get notified, and does the other kid's clone stay intact?

Disposition: Verified OK. The chat DM to the sponsor in DeclineQuestSheet fires unconditionally regardless of team vs. single mode. The other kid's clone is a fully independent chore row (different id), untouched by a sibling's decline — confirmed each clone pays out independently in approveGrandparentQuestAsParent. ChoreReviewSection's GpTurnedDownCard query (status === 'declined') already picks up a declined team clone too since it isn't filtered by team status. No fix needed.

Not a gap Kids don't have a "decline a household routine chore" submission-review action

Checked whether a kid's declined household chore ever needs to reach "Chore Reviews" the way a GP-quest decline does. On inspection, kids don't have a "decline a household routine chore" action at all today (only Can't-do-this on bounties/assigned chores pre-submission, which unassigns rather than declining a submission) — so this state doesn't actually exist as a reachable case. No fix needed.

Not a gap Kids/teens don't get System A's two-bounce negotiation (Snooze/Blocker/Trade/Discuss)

Judged intentional. System A's four-way pushback vocabulary (Snooze 48h, Blocker, Trade tasks, Discuss later) models a peer-to-peer household-logistics negotiation between two adults who both have full context on the family calendar and each other's workload — that doesn't map onto a parent-child chore relationship, where the parent is the authority, not a negotiating peer. The existing simpler flow (submit / can't-do-this-back-to-pool / resubmit-after-redo) is the age-appropriate analog and is now symmetric between kids and teens (see T1). Adding "Trade tasks" or "Snooze 48h" for a 10-year-old's chore would be over-engineering exactly as flagged in the task brief. No change made.

Not a gap A non-sponsor GP cannot see or act on another GP's sponsored quest

Verified via SponsorQuestsSection's mySponsored filter (sponsorUserId === active.id) and QuestsScreen.tsx's senior filter (q.sponsorUserId === myId). Two grandparents in the same family (e.g. paternal + maternal) each only ever see their own sponsored quests plus general inviteGrandparents invitations. This is correct — a quest one grandparent set up as a surprise/connection activity for their own grandkid should not be editable or visible-in-detail to the other GP by default. No change made.

Not a gap Sibling kids cannot see or approve each other's pending_approval submissions

Confirmed via QuestsScreen.tsx's isKidOrTeen filter block (only own-assigned + pool quests visible) and canApprove = isParentOrSenior && isReview — a sibling has no path to a decline/approve button for another kid's submission anywhere in the codebase. This is correct RBAC, not a gap.

Offline/optimistic-update rollback Every store mutation in choreStore.ts follows the same pattern: synchronous local set() (and AsyncStorage write) happens immediately, then dbUpdate/dbInsert fire the actual Supabase write fire-and-forget — confirmed by reading dbUpdate (choreStore.ts:613-620) and dbInsert (choreStore.ts:627-638): both only console.warn on error, neither is awaited by any mutator, and no mutator function anywhere in the file reverts its own local set() call if the corresponding DB write's promise later resolves with an error. Confirmed real gap — there is genuinely zero rollback anywhere in this store. A write that fails server-side (RLS rejection, network loss, constraint violation) leaves the local UI permanently showing the optimistic state as if it succeeded, with only a console warning nobody sees in production. The next full syncFromDB(force) (pull-to-refresh, or the next natural 60s-TTL refresh) would silently overwrite the wrong local state back to the true DB state — until then, the user sees success that didn't happen. See Finding N6. Not fixed this pass (a real fix requires a retry/rollback framework touching every mutator, out of scope for a targeted bug-fix pass) — flagged as a Known Gap.

Fixed N1 — Household Backlog's pool "disable" toggle silently did nothing, and was writing the wrong field anyway

features/hub/parent/backlog/PoolQuestCard.tsx:27,83-86

Scenario: A parent taps the lock/checkmark icon on a pool item in Household Backlog to "disable" it without deleting it. The button (line 83) calls updateChore(chore.id, { isPrivateParent: !isDisabled }) — but isDisabled itself (line 27) is read from (chore as any).isDisabled ?? false, a field nothing in the entire codebase ever sets (confirmed by a full-repo grep — the only occurrences of the string isDisabled are inside this one file, consuming a value nothing produces). So the icon always renders as "not disabled" no matter how many times it's tapped — every tap computes !false and writes isPrivateParent: true again, never toggling back.

Compounding issue: isPrivateParent: true is not an inert "hidden" flag — it actively hides the chore from every non-parent role (choreStore.ts:685, inside the realtime INSERT handler's visibility gate), excludes it from the parent's own review deck (getParentReviewDeck, choreStore.ts:2108), and removes it from the kid chore board (ChildChoreBoard.tsx:1064). A parent tapping what looks like a simple pause/disable toggle was actually reclassifying an ordinary household chore as parent-only-visible — a much bigger effect than "disable" implies, and one that also silently doesn't persist: isPrivateParent is not a real DB column (confirmed no is_private_parent column exists in any migration; choreFromRow, choreStore.ts:358, recomputes it purely from categoryType === 'parent_only_quest' on every load), so the "disable" silently reverts on next sync/reload too.

Fix: Added a real isDisabled?: boolean field to ChoreTask (store/choreStore.ts, alongside the other optional display flags), mapped it through choreFromRow/updateChore's DB patch (is_disabled column) so it persists and round-trips correctly, and changed PoolQuestCard.tsx's toggle to write { isDisabled: !isDisabled } instead of piggybacking on the unrelated, semantically-wrong, non-persistent isPrivateParent flag.

Gap, confirmed unreachable, not fixed N2 — Participant-row Approve/Decline/Reopen is dead code that can never render with live data

features/quests/components/QuestCard.tsx:563,594-617 · store/choreAdapter.ts:73-75,325-347

The Action Bible (Scenario 10 / Known Gaps) already flagged approveParticipant/declineParticipant/reopenParticipant as no-op stubs, and separately flagged the standard multi-assign form as "silently degrading to single-assign" because createParticipants was a no-op at the time that doc was written. Both of those framings are now stale — re-verified by direct code read this pass: createParticipants (choreAdapter.ts:325-344) is no longer a no-op; it clones a full independent chore row per selected kid (identical pattern to the GP team-bounty path), and AddQuestModal.tsx:387-390 does call it when 2+ kids are multi-selected. Multi-assign itself is fixed and working (re-confirmed, not re-guessed).

However, this makes the participant-row UI (QuestCard.tsx:594-617) structurally unreachable, not merely rare: choreToQuest (choreAdapter.ts:73-75) builds each Quest's participants array from that single ChoreTask row's own assignedToId only — c.assignedToId ? [oneEntry] : [] — so any one chore row can only ever produce 0 or 1 participant entries, never more, regardless of teamGroupId. Since createParticipants now fans a multi-assign out across N separate chore rows (each its own Quest object with its own single-entry participants array) instead of one row carrying N participants, q.participants.length > 1 can never become true anywhere in the current live data path. Fixed N5 — Pool claims and System-A responses had no optimistic-locking / compare-and-swap protection

store/choreStore.ts (claimBounty, respondToParentQuest)

Fix: both hot paths now send their own guarded DB write instead of going through the generic updateChore/dbUpdate unconditional-UPDATE path. claimBounty writes with .is('assigned_to_id', null) in the WHERE clause — only the first claim to actually land in Postgres succeeds; a 0-row result means someone else won the race, and the loser's optimistic local assignment is rolled back. respondToParentQuest writes with .eq('status', previousStatus) — if the assignment's status has already moved on by the time the write lands (another response got there first), the loser's optimistic local status update is reverted rather than silently overwriting the winner's outcome. updateChore itself was deliberately left as a generic, unconditional patch applier — it's used for hundreds of non-racy update shapes (editing a title, toggling a flag), and retrofitting a universal CAS into it would be the wrong-shaped fix for those callers.

Fixed — scoped N6 — No optimistic-update rollback on a failed DB write

The original finding was that rollback is absent store-wide, across every one of ~40 mutators built on the shared dbUpdate/dbInsert fire-and-forget helpers. A universal fix (retry queue, or awaiting every write and reverting every mutator's local set() on failure) is a genuine cross-cutting architectural rewrite, not a targeted fix, and was correctly out of scope as originally flagged.

What was actually fixed: the two highest-value, contention-prone paths from N5 — claimBounty and respondToParentQuest — now roll their own optimistic local update back to its prior value whenever their guarded write comes back with an error or a 0-row (lost-race) result, since those two already needed bespoke guarded writes for N5 and the rollback logic is a natural extension of that same code. The other ~38 mutators in the file still follow the store's original fire-and-forget pattern with no rollback — that remains a known, accepted architectural characteristic of this store, not silently fixed everywhere.

ScenarioFindingVerdict
Kid requests a cash-out for more points than they actually have requestCashOut (store/choreStore.ts:1502, pre-fix) only checked points < settings.minCashoutPoints — it never compared the requested amount against getMemberBalance(userId).total at all. Denying a cash-out — does the kid actually keep their points? denyCashOut (pre-fix) only appended [Denied] to the transaction's notes string. getMemberBalance (choreStore.ts:2299, pre-fix) treated every CASH_OUT-type transaction as an immediate, permanent deduction with no exception for a denied one — so the deduction requestCashOut applied the instant the request was filed was never reversed. The Deny confirmation dialog's own copy in ParentReviewDeck.tsx:269 — "Funds stay in their wallet" — was actively false: a denied request permanently shrank the kid's spend/save/give balance forever, identical in effect to an approved one. Fixed — see Finding N9. This was the most severe finding of this pass — not a race or an edge case, but a guaranteed, always-reachable bug on the ordinary "parent says no" path.

Not a gap — receipt reimbursement (dollars) and points/coins reward are two independent payouts by design, each fires exactly once, confirmed by reading both functions in full.
